# 디바이스 트리 (Device Tree)

> 「이 보드에 무엇이 어떻게 붙어 있는가」를 적은 자료 구조.
> 커널 코드가 아니라 **데이터**로 하드웨어 구성을 기술한다.

## 왜 필요한가

같은 SoC 를 쓰는 보드가 수백 종인데, 보드마다 커널을 따로 빌드할 수는 없다.
하드웨어 구성을 코드에서 빼내 별도 파일로 만든 것이 디바이스 트리다.

실무에서 이것을 만지는 순간은 대개 이렇다 —
**센서를 바꿨다 · 핀 배치가 다르다 · 새 보드 리비전이 왔다.**
드라이버는 그대로인데 연결 정보만 다를 때다.

## 최소 이해 수준

- **`.dts` 를 컴파일해 `.dtb` 로 만든다.** 부트로더가 `.dtb` 를 메모리에 올리고
  주소를 커널에 넘긴다. 커널은 그것을 읽어 장치를 만든다.
- **트리 구조다.** 버스 안에 장치가 들어가는 물리적 계층을 그대로 닮았다.

  ```dts
  &i2c1 {
      status = "okay";
      clock-frequency = <100000>;

      camera@1a {
          compatible = "sony,imx477";
          reg = <0x1a>;                    // I2C 주소
          reset-gpios = <&gpio0 17 GPIO_ACTIVE_LOW>;
          clocks = <&cam_clk>;
          status = "okay";
      };
  };
  ```

- **`compatible` 이 드라이버를 고른다.** 이 문자열이 드라이버의 매칭 표에 있는
  값과 같아야 바인딩된다. **오타 하나면 장치가 없는 것처럼 보인다.**
- **`reg` 는 문맥에 따라 뜻이 다르다.** I2C 아래면 주소, 메모리 맵 버스 아래면
  기준 주소와 크기다.
- **`status`** — `"okay"` 면 활성, `"disabled"` 면 커널이 무시한다.
  SoC 공통 파일에서 대부분 `disabled` 로 두고, 보드 파일에서 필요한 것만 켠다.
- **`.dtsi` 는 include 용.** SoC 공통을 `.dtsi` 로 두고 보드 `.dts` 가 포함한다.
  보드 파일에서 `&노드 { ... }` 로 덮어쓴다.
- **오버레이(`.dtbo`).** 본체를 건드리지 않고 일부만 얹는다.
  카메라 모듈 교체처럼 선택 사항인 하드웨어에 쓴다.
- **디바이스 트리는 드라이버가 아니다.** 「무엇이 붙었나」만 적는다.
  그 장치를 어떻게 다루는지는 드라이버 코드에 있다.

## 직접 해보기

### 1. 지금 동작 중인 트리 보기

커널은 실제로 쓰고 있는 트리를 `/proc` 에 노출한다.

```bash
ls /proc/device-tree/
cat /proc/device-tree/model; echo
cat /proc/device-tree/compatible | tr '\0' '\n'
```

**소스 파일이 아니라 여기를 봐야 한다.** 빌드한 것과 올라간 것이 다를 수 있다.

### 2. 트리를 읽기 쉬운 형태로 되돌리기

```bash
dtc -I fs -O dts /proc/device-tree -o /tmp/current.dts 2>/dev/null
grep -n -A8 'imx\|camera\|sensor' /tmp/current.dts | head -40
```

`.dtb` 파일이 있다면 그대로 풀 수도 있다.

```bash
dtc -I dtb -O dts board.dtb -o board.dts
```

### 3. 노드가 활성인지 확인

```bash
grep -r . /proc/device-tree/soc/i2c*/status 2>/dev/null | tr '\0' '\n'
```

`disabled` 면 커널이 그 장치를 아예 만들지 않는다.
`dmesg` 에 아무 로그가 없는 이유가 대개 이것이다.

### 4. 바인딩이 됐는지 확인

```bash
# 드라이버가 붙은 장치 목록
ls -l /sys/bus/i2c/devices/*/driver 2>/dev/null
ls /sys/bus/platform/drivers/
```

장치는 있는데 `driver` 심볼릭 링크가 없으면 **`compatible` 이 맞지 않은 것**이다.

### 5. 고쳐서 반영해 보기

```bash
# 컴파일
dtc -I dts -O dtb -o board.dtb board.dts

# 부트로더에서 올리는 경로에 배치한 뒤 재부팅
```

⚠ 잘못된 `.dtb` 로는 커널이 부팅하지 않는다.
**바꾸기 전 원본을 백업**하고, UART 콘솔을 붙여 둔 상태에서 한다.
→ [U-Boot](U-Boot.md) · [플래시 · 파일시스템](플래시와파일시스템.md)

### 6. 바인딩 문서 찾기

어떤 속성을 써야 하는지는 커널 소스에 문서로 있다.

```bash
find <커널소스>/Documentation/devicetree/bindings -iname '*imx*'
```

최근에는 YAML 스키마(`.yaml`)로 되어 있고, 검증도 가능하다.

```bash
make dt_binding_check
make dtbs_check
```

## 더 들어가면

- **phandle.** `<&gpio0 17 ...>` 처럼 다른 노드를 가리키는 참조다.
  뒤따르는 숫자의 개수와 의미는 **가리켜진 노드의 `#*-cells`** 가 정한다.
  `#gpio-cells = <2>` 면 GPIO 참조에 숫자 두 개가 온다.
- **pinctrl.** 핀 하나가 UART 도 되고 GPIO 도 되는 경우, 어느 기능으로 쓸지를
  `pinctrl-0` · `pinctrl-names` 로 지정한다. 핀 충돌은 여기서 난다.
- **regulator · clock 트리.** 전원과 클럭도 노드로 표현되고,
  장치가 `vdd-supply`·`clocks` 로 참조한다. **참조가 없으면 전원이 안 켜진다.**
- **`aliases` 와 `chosen`.** `chosen/bootargs` 가 커널 커맨드라인이고,
  `stdout-path` 가 콘솔이다. 부트로더 환경변수보다 **이쪽이 우선하는 경우가 있다.**
- **오버레이 적용 시점.** 부트로더에서 합치는 방식과 런타임에 얹는 방식이 있다.
  런타임 방식은 이미 바인딩된 장치와 충돌할 수 있다.
- **ACPI 와의 대비.** x86 은 펌웨어가 같은 역할을 한다. 임베디드 ARM/RISC-V 는
  디바이스 트리가 사실상 표준이다.

## 흔한 오해

### 「디바이스 트리를 고치면 드라이버가 생긴다」

생기지 않는다. 트리는 「여기 이런 칩이 있다」고 말할 뿐이다.
그 `compatible` 을 아는 드라이버가 커널에 없으면 아무 일도 안 일어난다.
**드라이버가 있는지 먼저 확인**한다.

```bash
grep -rn "sony,imx477" <커널소스>/drivers/media/
```

### 「소스의 `.dts` 를 보면 현재 구성을 안다」

빌드된 `.dtb` 가 플래시의 어디에 있고 부트로더가 어느 것을 올리는지가 따로 있다.
소스를 고쳤는데 반영이 안 되는 흔한 원인이 **다른 `.dtb` 가 올라가고 있는 것**이다.
`/proc/device-tree` 를 기준으로 판단한다.

### 「`status` 만 `okay` 로 바꾸면 켜진다」

전원 · 클럭 · 핀 설정 참조가 함께 있어야 한다.
셋 중 하나라도 빠지면 프로브가 실패하고 `dmesg` 에 `-EPROBE_DEFER` 나
`failed to get ...` 가 남는다. **그 메시지가 무엇이 빠졌는지 알려준다.**

### 「부팅이 되니 트리는 맞다」

부팅과 주변장치는 별개다. 콘솔과 저장장치만 맞아도 부팅은 된다.
카메라가 안 잡히는 것은 부팅 성공과 무관하다.
