# 크로스 컴파일

> 지금 쓰는 PC 에서, 다른 종류의 프로세서에서 돌아갈 프로그램을 만드는 것.

## 왜 필요한가

임베디드 보드에는 컴파일러를 둘 수 없다. 플래시가 수십 MB 이고 CPU 가 느리다.
그래서 **개발은 PC 에서, 실행은 보드에서** 한다.

IP카메라 작업에서는 거의 모든 것이 이 경로를 지난다 — 암호 라이브러리·웹서버·
스트리밍 서버·자체 데몬. 「보드에 없는 도구를 쓰려면」의 답이 항상 크로스 컴파일이다.

## 최소 이해 수준

- **툴체인은 접두어로 구분한다.**
  `riscv64-<벤더>-linux-gnu-gcc` 처럼 `<아키텍처>-<벤더>-<OS>-<ABI>-` 형태다.
  `CROSS_COMPILE` 환경변수에 접두어까지 넣는 관례가 굳어 있다.
- **`sysroot` 가 대상 시스템의 `/` 역할을 한다.**
  대상용 헤더와 라이브러리가 여기 들어 있다. 실수로 호스트 헤더를 쓰면
  컴파일은 되고 실행은 안 되는 상태가 된다.
- **정적 링크 vs 동적 링크.**
  정적은 라이브러리를 실행파일에 넣어 보드에 `.so` 를 둘 필요가 없다. 크기가 커지지만
  의존성 문제가 사라진다. 플래시가 빠듯한 제품에서는 판단이 갈린다.
- **`file` 로 확인한다.**
  만든 결과가 정말 대상용인지 가장 빨리 확인하는 방법이다.
- **에뮬레이터로 호스트에서 돌려볼 수 있다.**
  `qemu-<arch>-static` 에 `-L <sysroot>` 를 주면 대상 바이너리를 PC 에서 실행한다.
  보드에 올리기 전에 「적어도 시작은 되는가」를 확인할 수 있다.
- **빌드 시스템이 대신 해주는 경우가 많다.**
  Buildroot·Yocto 는 툴체인 준비부터 패키지 교차 빌드까지 묶어 준다.
  단독 라이브러리 하나를 급히 올려야 할 때는 직접 하는 편이 빠르다.

## 직접 해보기

### 1. 툴체인 확인

```bash
export PATH=/opt/<툴체인>/bin:$PATH
riscv64-<벤더>-linux-gnu-gcc --version
riscv64-<벤더>-linux-gnu-gcc -print-sysroot
```

`-print-sysroot` 가 비어 있으면 `--sysroot=` 를 직접 줘야 한다.

### 2. 가장 작은 것부터

```bash
cat > t.c <<'EOF'
#include <stdio.h>
int main(void){ printf("hello\n"); return 0; }
EOF

riscv64-<벤더>-linux-gnu-gcc -static -o t t.c
file t
```

기대 출력:

```
t: ELF 64-bit LSB executable, UCB RISC-V, ..., statically linked
```

**`x86-64` 가 나오면 호스트 gcc 가 잡힌 것이다.** `PATH` 를 먼저 의심한다.

### 3. 보드에 올리기 전에 호스트에서 돌려보기

```bash
qemu-riscv64-static -L /opt/<툴체인>/sysroot ./t
```

`hello` 가 나오면 링크와 로더 경로가 성립한 것이다.

⚠ 데몬처럼 무한 루프를 도는 프로그램은 인자 없이 실행하면 붙잡힌다.
`--version` 같은 무해한 서브커맨드로 확인한다.

### 4. 실제 라이브러리 하나 빌드해 보기

OpenSSL 이 좋은 연습 대상이다 — 거의 모든 프로젝트가 쓰고, 크로스 빌드 옵션이
잘 정리돼 있다.

```bash
./Configure linux64-riscv64 no-shared \
    --prefix=/usr --openssldir=/etc/ssl \
    --cross-compile-prefix=riscv64-<벤더>-linux-gnu-
make -j$(nproc)
file libcrypto.a
```

`no-shared` 로 정적 라이브러리만 만든다. `--prefix`·`--openssldir` 이 **바이너리에
문자열로 박히므로** 호스트 경로를 그대로 두면 안 된다.

### 5. 빌드 경로가 남았는지 검사

```bash
strings <바이너리> | grep -E "$HOME|/home/" | head
```

아무것도 안 나와야 한다. 나오면 [아래](#빌드-경로가-바이너리에-남는-두-경로) 참고.

## 더 들어가면

- **ABI 와 부동소수점.**
  RISC-V 의 `lp64d`, ARM 의 `eabihf` 처럼 ABI 가 다르면 링크되지 않는다.
  툴체인과 기존 라이브러리의 ABI 가 같아야 한다.
- **`pkg-config` 오염.**
  호스트의 `.pc` 파일을 읽어 호스트 라이브러리를 링크하려 드는 일이 흔하다.
  `PKG_CONFIG_SYSROOT_DIR`·`PKG_CONFIG_LIBDIR` 을 대상 쪽으로 고정한다.
- **CMake 툴체인 파일.**
  `CMAKE_SYSTEM_NAME`·`CMAKE_C_COMPILER`·`CMAKE_FIND_ROOT_PATH` 를 적어 한 파일로 관리한다.
- **재현 가능한 빌드.**
  같은 소스에서 같은 바이너리가 나오게 하는 것. `SOURCE_DATE_EPOCH`·경로 치환·
  압축 옵션 고정이 필요하다. 공급망 검증에서 요구될 수 있다.

## 흔한 오해

### 「정적 링크하면 대상에 라이브러리가 전혀 필요 없다」

대개 맞지만 예외가 있다.

```
warning: Using 'getaddrinfo' in statically linked applications requires
at runtime the shared libraries from the glibc version used for linking
```

이름 해석(NSS)이 런타임에 공유 라이브러리를 `dlopen` 하기 때문이다.
IP 주소로만 접속하는 구성이면 실무상 문제가 없지만, **호스트명을 쓰는 순간 드러난다.**
`gethostbyname` 도 같은 경고가 나온다.

### 「컴파일이 되면 대상에서 돈다」

호스트 헤더를 섞어 쓰면 컴파일은 통과하고 실행에서 깨진다.
`file` 로 아키텍처를 확인하고, 에뮬레이터로 한 번 돌려보는 두 단계가 싸다.

### 「빌드 경로는 디버그 정보에만 남는다」

`strip` 해도 남는 경로가 있다. 원인이 둘이고 대책이 다르다.

#### 빌드 경로가 바이너리에 남는 두 경로

**① 라이브러리의 설정 경로 상수**
OpenSSL 의 `openssldir` 처럼 빌드 시 고정되는 값. 중립적인 경로로 다시 빌드해야 한다.

**② `__FILE__` 매크로**
소스 절대경로가 박힌다. `-ffile-prefix-map=<원본>=<치환>` 으로 바꾼다.

⚠ ②의 함정 — 일부 라이브러리는 **컴파일 명령줄 문자열 자체**를 바이너리에 넣는다.
그러면 `-ffile-prefix-map=/home/사용자=/build` 라는 **인자에 적힌 절대경로가 그대로 남는다.**
빌드 디렉터리 안에서 상대경로로 지정해야 0 건이 된다.

```bash
# 나쁨 — 인자에 홈 경로가 들어가 그게 박힌다
-ffile-prefix-map=$HOME=/build

# 좋음 — 빌드 디렉터리에서 상대경로로
cd <빌드디렉터리> && ... -ffile-prefix-map=.=<프로젝트명>
```

### 「Buildroot 나 Yocto 를 써야 제대로다」

전체 이미지를 만들 때는 그렇다. 하지만 **바이너리 하나를 급히 보드에 올려야 할 때**
빌드 시스템을 통과시키는 비용이 직접 빌드보다 크다.
둘을 섞어 쓰는 것이 실무다 — 이미지는 빌드 시스템으로, 급한 것은 직접.
