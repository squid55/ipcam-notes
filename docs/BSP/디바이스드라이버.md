# 디바이스 드라이버 작성

> 하드웨어를 커널의 표준 인터페이스에 연결하는 코드.
> 「이 칩을 리눅스가 아는 장치로 보이게 만드는 일」이다.

## 왜 필요한가

카메라를 새로 붙였을 때 드라이버가 없으면 **`/dev/video0` 이 생기지 않는다.**
응용 코드를 아무리 잘 써도 시작할 수가 없다.

그리고 대부분의 실무는 처음부터 쓰는 것이 아니라 **비슷한 드라이버를 고치는 일**이다.
구조를 알면 어디를 고쳐야 하는지가 보인다.

## 최소 이해 수준

- **드라이버는 프레임워크에 등록하는 것이다.** 직접 파일 조작을 다 구현하지 않고,
  해당 서브시스템(V4L2 · 네트워크 · 입력 등)이 요구하는 콜백을 채운다.
  **그 서브시스템이 유저 공간 인터페이스를 대신 만들어 준다.**
- **버스 드라이버 모델.** 장치는 버스에 붙어 있고, 드라이버는 버스에 등록한다.
  커널이 `compatible` 이나 ID 로 짝을 찾아 `probe()` 를 부른다.

  ```
  디바이스트리 노드  ──→  커널이 device 객체 생성
                              ↓  compatible 매칭
                        드라이버의 probe() 호출
                              ↓
                   리소스 확보 → 하드웨어 초기화 → 서브시스템 등록
  ```

- **최소 골격(I2C 장치).**
  ```c
  static int foo_probe(struct i2c_client *client)
  {
      struct foo *st = devm_kzalloc(&client->dev, sizeof(*st), GFP_KERNEL);
      if (!st) return -ENOMEM;
      st->regu = devm_regulator_get(&client->dev, "vdd");
      if (IS_ERR(st->regu)) return PTR_ERR(st->regu);
      /* 칩 ID 읽어 확인 → 실패하면 -ENODEV */
      /* 서브시스템에 등록 */
      return 0;
  }

  static const struct of_device_id foo_of_match[] = {
      { .compatible = "vendor,foo123" },
      { }
  };
  MODULE_DEVICE_TABLE(of, foo_of_match);

  static struct i2c_driver foo_driver = {
      .driver = { .name = "foo", .of_match_table = foo_of_match },
      .probe  = foo_probe,
      .remove = foo_remove,
  };
  module_i2c_driver(foo_driver);
  MODULE_LICENSE("GPL");
  ```
  `compatible` 문자열이 디바이스트리의 것과 **글자 하나까지 같아야** 한다.
  → [디바이스 트리](디바이스트리.md)

- **`devm_` 접두사를 쓴다.** `devm_kzalloc` · `devm_regulator_get` 등은
  **장치가 사라질 때 자동으로 해제**된다. 오류 처리 경로가 크게 짧아진다.
  손으로 해제하는 코드를 쓰면 누락이 생긴다.
- **오류는 음수 errno 로 돌린다.** `-ENOMEM` · `-EINVAL` · `-ENODEV` · `-EPROBE_DEFER`.
  `-EPROBE_DEFER` 는 「아직 준비가 안 됐으니 나중에 다시 불러 달라」는 뜻이고,
  **의존 장치(클럭·레귤레이터)가 늦게 올라올 때** 쓴다.
- **유저 공간 접점이 세 가지.**
  - 문자 디바이스 (`/dev/...`) — `read`·`write`·`ioctl`
  - sysfs 속성 (`/sys/...`) — 작은 값 하나를 텍스트로
  - 서브시스템 표준 API — V4L2 · ALSA · netdev. **가능하면 이쪽을 쓴다**
- **잠금이 필요하다.** 여러 프로세스가 동시에 열 수 있고, 인터럽트가 끼어든다.
  뮤텍스(잠들 수 있는 문맥)와 스핀락(인터럽트 문맥)을 구분해 쓴다.
- **커널에서는 `printf` 대신 `dev_*`.**
  ```c
  dev_err(&client->dev,  "칩 ID 불일치: 0x%04x\n", id);
  dev_info(&client->dev, "준비됨\n");
  dev_dbg(&client->dev,  "레지스터 0x%02x = 0x%02x\n", a, v);
  ```
  `dev_*` 는 **어느 장치가 낸 로그인지 자동으로 붙여 준다.**

## 직접 해보기

### 1. 비슷한 드라이버를 찾아 읽기

새 센서를 붙일 때 가장 빠른 출발점이다.

```bash
ls drivers/media/i2c/ | head -40
wc -l drivers/media/i2c/imx*.c | sort -n
```

**가장 짧은 것부터 읽는다.** 구조는 같고 레지스터 표만 다르다.

### 2. 최소 모듈을 만들어 올려 보기

```c
/* hello.c */
#include <linux/module.h>
static int __init hello_init(void) { pr_info("hello: 올라옴\n"); return 0; }
static void __exit hello_exit(void) { pr_info("hello: 내려감\n"); }
module_init(hello_init);
module_exit(hello_exit);
MODULE_LICENSE("GPL");
```

```makefile
# Makefile
obj-m := hello.o
```

```bash
make -C /lib/modules/$(uname -r)/build M=$PWD modules
sudo insmod hello.ko && dmesg | tail -3
sudo rmmod hello && dmesg | tail -3
```

**이것이 도는 것을 먼저 확인**하고 나서 실제 드라이버로 간다.
빌드 환경 문제와 드라이버 논리 문제를 섞지 않는 것이 중요하다.

### 3. probe 가 불렸는지 확인

```bash
dmesg | grep -i <드라이버이름>
ls -l /sys/bus/i2c/devices/*/driver
```

`driver` 링크가 없으면 매칭이 안 된 것이다 — `compatible` 을 대조한다.

```bash
cat /proc/device-tree/.../compatible | tr '\0' '\n'
modinfo <드라이버>.ko | grep alias
```

### 4. probe 가 실패한 이유 보기

```bash
dmesg | grep -iE 'probe|failed|defer|EPROBE'
```

`-517` 이 `-EPROBE_DEFER` 다. 계속 반복되면 **의존 리소스가 끝내 안 올라온 것**이므로
디바이스트리의 클럭·레귤레이터 참조를 확인한다.

### 5. 디버그 로그 켜기

`dev_dbg` 는 기본적으로 출력되지 않는다.

```bash
# 동적 디버그로 파일 단위로 켜기
echo 'file drivers/media/i2c/foo.c +p' | sudo tee /sys/kernel/debug/dynamic_debug/control
dmesg -w
```

`CONFIG_DYNAMIC_DEBUG` 가 켜져 있어야 한다.

### 6. sysfs 속성 하나 만들어 보기

```c
static ssize_t temp_show(struct device *dev, struct device_attribute *a, char *buf)
{
    return sysfs_emit(buf, "%d\n", read_temp(dev));
}
static DEVICE_ATTR_RO(temp);
/* probe 에서: device_create_file(dev, &dev_attr_temp); */
```

```bash
cat /sys/bus/i2c/devices/1-001a/temp
```

**한 파일에 한 값**이 sysfs 규칙이다. 여러 값을 한 파일에 넣으면 리뷰에서 거부된다.

### 7. 코드 스타일 검사

```bash
scripts/checkpatch.pl --strict -f drivers/media/i2c/foo.c
```

메인라인에 보내지 않더라도 돌려 두면 흔한 실수가 잡힌다.

## 더 들어가면

- **V4L2 서브디바이스 모델.** 센서 드라이버는 `v4l2_subdev` 로 등록하고,
  브리지(ISP·CSI 수신기)가 그것을 묶어 `/dev/video*` 를 만든다.
  `v4l2_subdev_ops` 의 `pad` 연산으로 포맷을 협상한다. → [V4L2](../영상/V4L2.md)
- **regmap.** I2C·SPI 레지스터 접근을 추상화하고 캐시까지 해 준다.
  직접 `i2c_smbus_*` 를 부르는 대신 `devm_regmap_init_i2c` 를 쓰면 코드가 짧아진다.
- **DMA 와 일관성.** 장치가 직접 메모리에 쓰면 CPU 캐시와 어긋난다.
  `dma_map_single` · `dma_alloc_coherent` 로 관리한다.
  영상 드라이버 성능의 핵심이 이 부분이다.
- **전원 관리.** `runtime_pm` 으로 쓰지 않을 때 전원을 내린다.
  `pm_runtime_get_sync` / `put` 쌍이 맞지 않으면 장치가 꺼진 채 접근한다.
- **트리 밖(out-of-tree) 드라이버의 비용.** 커널 내부 API 가 바뀌면 매번 고쳐야 한다.
  **메인라인에 넣으면 다른 사람이 같이 고쳐 준다** — 그것이 가장 큰 이점이다.
- **디버깅 수단.** `ftrace` 로 함수 호출을 추적하고, `kgdb` 로 중단점을 잡고,
  `KASAN` 으로 메모리 오류를 잡는다. 커널은 `printk` 만으로 버티기 어렵다.

## 흔한 오해

### 「드라이버를 쓰면 `/dev` 노드를 직접 만들어야 한다」

서브시스템이 만들어 준다. V4L2 에 등록하면 `/dev/videoN` 이 생기고,
문자 디바이스로 직접 등록할 때만 `alloc_chrdev_region` 이 필요하다.
**직접 만드는 길로 가면 표준 도구(`v4l2-ctl` 등)를 못 쓴다.**

### 「probe 에서 하드웨어를 다 초기화해야 한다」

전원을 올려 두면 쓰지 않을 때도 전력을 먹는다. `probe` 에서는
**존재 확인(칩 ID 읽기)만 하고** 실제 스트리밍 시작 때 초기화하는 편이 낫다.

### 「모듈이 올라갔으니 드라이버가 동작한다」

모듈 적재와 `probe` 호출은 별개다. `lsmod` 에 있는데 `probe` 가 안 불렸다면
매칭이 안 된 것이다. **`dmesg` 와 `/sys/bus/*/devices/*/driver` 를 봐야** 구분된다.

### 「커널 코드도 C 니까 똑같이 쓰면 된다」

표준 C 라이브러리가 없다. `malloc`·`printf`·부동소수 연산을 쓸 수 없고,
스택이 작으며(보통 8~16KB), 잠들 수 있는 문맥과 그렇지 않은 문맥이 구분된다.
**인터럽트 핸들러에서 뮤텍스를 잡으면 시스템이 멈춘다.**

### 「오류를 `-1` 로 돌려도 된다」

`-1` 은 `-EPERM` 이다. 호출자가 「권한 없음」으로 해석한다.
의미에 맞는 errno 를 골라야 상위 계층과 유저 공간이 옳게 반응한다.
