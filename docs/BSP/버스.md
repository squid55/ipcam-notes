# UART · I2C · SPI · GPIO

> 보드 위의 칩끼리 이야기하는 네 가지 방법. 영상 데이터가 아니라
> **설정과 제어**가 여기로 오간다.

## 왜 필요한가

카메라 모듈이 안 잡힐 때 「드라이버 문제인가 배선 문제인가」를 가르는 자리가 여기다.
`i2cdetect` 한 번이면 전원과 클럭이 들어갔는지가 판가름 난다.

그리고 UART 콘솔은 커널이 부팅 도중 죽었을 때 **유일하게 남는 창**이다.
네트워크가 올라오기 전에 무슨 일이 있었는지는 여기서만 볼 수 있다.

## 최소 이해 수준

| | 선 개수 | 속도 | 장치 수 | 주 용도 |
|---|---|---|---|---|
| **UART** | 2 (TX·RX) | ~115200bps | 1:1 | 콘솔 · 디버그 로그 |
| **I2C** | 2 (SCL·SDA) | 100k~1Mbps | 여러 개 (주소로 구분) | 센서 레지스터 설정 · EEPROM |
| **SPI** | 4 (SCLK·MOSI·MISO·CS) | ~수십 Mbps | 여러 개 (CS 선마다 하나) | 플래시 · 디스플레이 |
| **GPIO** | 1 | — | — | 리셋 · 전원 인가 · LED · 인터럽트 |

- **UART 는 클럭선이 없다.** 양쪽이 같은 속도(보율)로 약속해야 한다.
  속도가 틀리면 **글자가 깨져 나온다** — 아무것도 안 나오는 것과 구분된다.
- **UART 는 크로스로 연결한다.** 한쪽 TX 를 상대 RX 에.
  GND 를 반드시 공통으로 잇는다. 이것을 빠뜨리면 아무것도 안 보인다.
- **I2C 는 주소로 장치를 고른다.** 7비트 주소라 최대 127개.
  **같은 주소를 쓰는 칩 두 개를 한 버스에 달면 충돌**한다.
  그래서 칩마다 주소 선택 핀이 있거나 버스를 나눈다.
- **I2C 에는 풀업 저항이 필요하다.** 오픈 드레인이라 저항이 없으면 신호가 안 올라간다.
  보통 보드에 이미 있지만, 모듈을 직접 붙일 때 빠뜨리기 쉽다.
- **SPI 는 전이중이고 빠르다.** 대신 장치마다 CS 선이 하나씩 필요해 핀을 많이 쓴다.
- **GPIO 는 핀 하나를 0/1 로 다루는 것**이다. 카메라 모듈의 리셋 · 전원 인가 순서가
  대개 GPIO 로 제어되고, **순서와 대기 시간이 데이터시트에 정해져 있다.**
- **모든 배선은 디바이스트리에 적힌다.** 어느 I2C 버스에 어느 주소로 붙었는지,
  리셋이 몇 번 GPIO 인지. → [디바이스 트리](디바이스트리.md)

## 직접 해보기

### 1. UART 콘솔 붙이기

USB-시리얼 어댑터를 TX↔RX 크로스로, GND 는 공통으로 연결한다.

```bash
ls /dev/ttyUSB* /dev/ttyACM*
picocom -b 115200 /dev/ttyUSB0
# 또는
screen /dev/ttyUSB0 115200
```

- 아무것도 안 나온다 → 배선 · GND · 전원 확인
- 깨진 글자가 나온다 → **보율이 틀렸다.** 9600 · 57600 · 115200 순으로 시도
- 부팅 로그는 나오는데 입력이 안 먹는다 → TX 선만 연결됐거나 콘솔 입력이 막혀 있다

⚠ 3.3V 어댑터인지 확인한다. 5V 를 3.3V 핀에 넣으면 칩이 죽는다.

### 2. I2C 버스 훑기

```bash
ls /dev/i2c-*
i2cdetect -l              # 버스 목록
i2cdetect -y -r 1         # 1번 버스 스캔
```

주소 자리에 값이 뜨면 그 칩은 살아 있다.
**뜨지 않으면 소프트웨어 문제가 아니다** — 전원 · 클럭 · 배선 · 풀업을 본다.

```bash
i2cget -y 1 0x36 0x00     # 레지스터 하나 읽기
```

⚠ `i2cdetect` 는 쓰기를 시도하는 주소가 있어 일부 칩의 상태를 바꿀 수 있다.
`-r` 로 읽기 방식을 쓰는 편이 안전하다.

### 3. 센서 칩 ID 읽어 보기

대부분의 이미지 센서는 특정 레지스터에 고정된 ID 를 갖는다.
데이터시트에서 그 주소를 찾아 읽으면 「통신이 되는지」가 한 번에 확인된다.

```bash
i2cget -y 1 0x1a 0x30 w   # 예: 칩 ID 레지스터
```

기대값이 나오면 I2C 는 정상이고, 문제는 위 계층에 있다.

### 4. GPIO 만져 보기

```bash
gpiodetect
gpioinfo
gpioget gpiochip0 17
gpioset gpiochip0 17=1
```

옛 방식(`/sys/class/gpio`)은 폐기 예정이다. `libgpiod` 쪽을 쓴다.

⚠ **이미 드라이버가 잡은 핀은 건드릴 수 없다.** `gpioinfo` 에 `[used]` 로 표시된다.
억지로 바꾸면 드라이버 상태와 실제가 어긋난다.

### 5. SPI 플래시 확인

```bash
ls /dev/spidev*
cat /proc/mtd
dmesg | grep -i spi
```

### 6. 커널이 무엇을 인식했는지

```bash
ls /sys/bus/i2c/devices/
ls /sys/bus/spi/devices/
dmesg | grep -iE 'i2c|spi|gpio' | head -40
```

디바이스트리에 적었는데 여기 없으면 노드가 `disabled` 이거나 드라이버가 없다.

## 더 들어가면

- **I2C 클럭 스트레칭.** 느린 장치가 SCL 을 붙잡아 시간을 번다.
  일부 컨트롤러는 이것을 제대로 못 다뤄서 통신이 깨진다.
- **I2C 버스 멈춤.** 전송 도중 리셋되면 슬레이브가 SDA 를 붙잡은 채 굳는다.
  클럭을 9번 넣어 풀어주는 복구 절차가 있다.
- **UART 흐름 제어.** RTS/CTS 를 안 쓰면 빠른 로그가 넘칠 때 글자가 사라진다.
  부팅 로그가 중간중간 잘려 보이면 이것을 의심한다.
- **버스 속도 낮추기.** 배선이 길거나 노이즈가 있으면 I2C 를 100kHz 로 낮춘다.
  디바이스트리의 `clock-frequency` 로 바꾼다.
- **로직 애널라이저.** 파형을 보면 「신호가 아예 없는지」와
  「신호는 있는데 응답이 없는지」가 갈린다. 이 구분이 시간을 가장 많이 아낀다.

## 흔한 오해

### 「`i2cdetect` 에 안 뜨면 드라이버를 고쳐야 한다」

반대다. 안 뜨는 것은 **드라이버 아래 계층**의 문제다.
드라이버를 아무리 고쳐도 전원이 안 들어온 칩은 응답하지 않는다.

### 「GPIO 로 리셋만 토글하면 된다」

전원 인가 → 클럭 안정 대기 → 리셋 해제 → 추가 대기, 순서와 시간이 정해져 있다.
데이터시트의 파워온 시퀀스를 지키지 않으면 **간헐적으로만 실패**한다.
가장 찾기 어려운 종류의 버그다.

### 「UART 콘솔은 개발용이니 제품에도 남겨도 된다」

남기면 물리적으로 접근한 사람이 부트로더 셸이나 루트 셸을 얻을 수 있다.
제품에서는 콘솔 입력을 막거나 헤더를 제거한다.
**「남아 있다」는 사실 자체를 문서에 적어야 한다** — 적지 않은 것이 더 문제가 된다.
→ [U-Boot](U-Boot.md)

### 「SPI 가 I2C 보다 항상 낫다」

빠르지만 핀을 많이 쓰고 장치 수만큼 CS 선이 필요하다.
초당 몇 번 레지스터를 읽는 용도라면 I2C 로 충분하다.
