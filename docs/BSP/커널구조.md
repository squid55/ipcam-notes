# 커널 구조 · 모듈

> 리눅스 커널이 어떤 덩어리로 나뉘어 있고, 그중 일부를 따로 빌드해
> 나중에 끼워 넣는 방법이 모듈이다.

## 왜 필요한가

임베디드에서 커널을 만지는 일은 대개 셋 중 하나다 —
**설정을 바꿔 기능을 켜거나 끄기 · 드라이버를 붙이기 · 부팅이 멈춘 원인 찾기.**
전체 구조를 알아야 「이 문제가 커널 안인지 밖인지」가 먼저 갈린다.

그리고 커널 버전과 설정이 나머지 전부의 전제다. 센서 드라이버가 있는지,
V4L2 기능이 켜져 있는지, 파일시스템을 마운트할 수 있는지가 여기서 정해진다.

## 최소 이해 수준

- **모놀리식이지만 모듈을 지원한다.** 커널 기능 전부가 한 주소 공간에서 돌고,
  일부를 `.ko` 파일로 떼어 실행 중에 넣고 뺄 수 있다.
- **큰 덩어리.**
  ```
  프로세스 관리 · 스케줄러       누가 CPU 를 쓸지
  메모리 관리 (MM)              가상 주소 · 페이지 · 슬랩
  가상 파일시스템 (VFS)         ext4·ubifs·procfs 를 같은 인터페이스로
  네트워크 스택                 소켓 · TCP/IP · netfilter
  디바이스 드라이버             전체 소스의 절반 이상을 차지한다
  아키텍처 의존 코드 (arch/)    부팅 · 인터럽트 · 원자적 연산
  ```
- **소스 트리 배치.**

  | 디렉터리 | 내용 |
  |---|---|
  | `arch/` | CPU 별 코드. `arch/riscv`, `arch/arm64` |
  | `drivers/` | 장치 드라이버. `drivers/media/i2c/` 에 센서들이 있다 |
  | `fs/` | 파일시스템 |
  | `net/` | 네트워크 스택 |
  | `kernel/` | 스케줄러 · 시그널 · 시간 |
  | `mm/` | 메모리 관리 |
  | `include/` | 헤더. `include/uapi/` 는 **유저 공간과 공유하는** 것 |
  | `Documentation/` | 공식 문서. 1차 출처로 자주 쓴다 |

- **`Kconfig` 와 `.config`.** 기능마다 `Kconfig` 항목이 있고,
  `.config` 가 이번 빌드에서 무엇을 켰는지를 담는다. 값은 셋이다.
  ```
  y   커널에 내장
  m   모듈로 빌드 (.ko)
  n   빌드하지 않음
  ```
- **내장이냐 모듈이냐의 기준.** **부팅에 필요한 것은 내장**이어야 한다.
  루트 파일시스템 드라이버를 모듈로 두면 그것을 읽으려고 루트를 마운트해야 하는
  순환에 빠진다(initramfs 로 푸는 방법이 있다).
- **모듈 도구.**
  ```
  lsmod              올라간 모듈 목록
  modinfo <이름>      설명 · 매개변수 · 의존성
  insmod <파일>.ko    파일을 직접 넣는다 (의존성 처리 안 함)
  modprobe <이름>     의존성까지 같이 넣는다
  rmmod <이름>        뺀다 (쓰는 중이면 실패)
  ```
- **커널 버전 표기.** `6.12.59-cip14` 처럼 뒤에 붙는 것이 배포·패치 계열이다.
  `cip` · `rt` · 벤더 접미사는 **장기 지원이나 특수 패치**가 들어갔다는 뜻이다.
  임베디드 제품은 장기 지원(SLTS/LTS) 계열을 고른다.
- **GPL 이다.** 커널에 링크되는 코드는 GPL 의무를 진다.
  벤더가 독자 드라이버를 사용자 공간으로 빼거나 얇은 GPL 래퍼를 두는 이유가 이것이다.

## 직접 해보기

### 1. 지금 도는 커널 확인

```bash
uname -a
cat /proc/version
cat /proc/cmdline
```

`/proc/cmdline` 이 부트로더가 넘긴 인자다. `root=` · `console=` 이 여기 있다.
→ [U-Boot](U-Boot.md)

### 2. 무엇이 켜져 있는지 확인

```bash
# 설정이 노출돼 있으면
zcat /proc/config.gz | grep -E 'CONFIG_VIDEO_DEV|CONFIG_UBIFS_FS|CONFIG_MODULES'
# 없으면
grep -E 'CONFIG_VIDEO_DEV' /boot/config-$(uname -r)
```

`=y` 는 내장, `=m` 은 모듈, 주석(`# ... is not set`)이면 없는 것이다.
**「기능이 안 된다」의 상당수가 여기서 설명된다.**

### 3. 모듈 상태 보기

```bash
lsmod
modinfo uvcvideo 2>/dev/null | head -20
ls /lib/modules/$(uname -r)/kernel/drivers/media/i2c/ 2>/dev/null
```

빌드된 드라이버 파일이 있는데 `lsmod` 에 없으면 **자동으로 올라가지 않은 것**이다.
`modprobe` 로 직접 올려 본다.

### 4. 커널 메시지 읽기

```bash
dmesg | less
dmesg -l err,warn
dmesg -w            # 실시간으로 따라가기
```

부팅 실패를 볼 때는 **콘솔로 보는 것이 유일한 방법**인 경우가 많다.
`dmesg` 는 부팅이 끝나야 볼 수 있다. → [UART · I2C · SPI · GPIO](버스.md)

### 5. 커널을 실제로 빌드해 보기

```bash
export ARCH=riscv CROSS_COMPILE=<툴체인 접두사>
make <보드>_defconfig
make menuconfig            # 항목 검색은 '/' 키
make -j$(nproc)
ls arch/riscv/boot/Image*
```

⚠ `make menuconfig` 에서 바꾼 것은 `.config` 에 들어간다.
**`make <보드>_defconfig` 를 다시 돌리면 덮어써진다.**
바꾼 내용을 남기려면 `make savedefconfig` 로 최소 설정을 뽑아 보관한다.

→ [크로스 컴파일](크로스컴파일.md)

### 6. 모듈만 따로 빌드

```bash
make modules
make modules_install INSTALL_MOD_PATH=/tmp/rootfs
```

⚠ **모듈은 빌드한 커널과 버전·설정이 맞아야** 올라간다.
`version magic` 이 다르면 `insmod` 가 거부한다.

```bash
modinfo <파일>.ko | grep vermagic
cat /proc/version
```

### 7. 무엇이 커널 밖인지 확인

문제가 커널인지 응용인지 가르는 가장 빠른 방법이다.

```bash
strace -f -e trace=ioctl,openat <프로그램> 2>&1 | head -30
```

시스템 콜이 실패하면 커널·드라이버 쪽, 호출 자체가 없으면 응용 쪽이다.

## 더 들어가면

- **시스템 콜 경계.** 유저 공간은 시스템 콜로만 커널에 들어간다.
  ABI 는 **절대 깨지지 않는다는 규칙**이 있어서 옛 바이너리가 새 커널에서 돈다.
  반면 커널 내부 API 는 언제든 바뀌므로, 트리 밖 드라이버는 계속 손봐야 한다.
- **`/proc` · `/sys` · `debugfs`.** 커널 상태를 파일로 노출하는 세 창구.
  `/sys` 가 장치 계층 구조를 반영하고, `debugfs` 는 디버깅 전용이다.
- **인터럽트와 하반부.** 인터럽트 핸들러는 짧아야 하므로 무거운 일은
  softirq · tasklet · workqueue 로 미룬다. 드라이버 설계의 기본 골격이다.
- **선점과 실시간.** `PREEMPT_RT` 를 쓰면 지연의 최악값이 줄어든다.
  영상 파이프라인의 프레임 누락을 줄이는 데 쓰이지만 전체 처리량은 약간 떨어진다.
- **initramfs.** 루트를 마운트하기 전에 메모리에서 도는 임시 루트.
  루트 파일시스템 검증이나 암호 해제를 여기서 한다.
  → [무결성과 서명 업데이트](../보안/무결성과서명업데이트.md)
- **`defconfig` 관리.** 제품 설정은 `arch/*/configs/` 에 `_defconfig` 로 넣어
  **형상관리 대상으로 둔다.** `.config` 파일 자체를 저장소에 넣으면 잡음이 많다.

## 흔한 오해

### 「커널을 새로 빌드하면 기능이 생긴다」

드라이버 코드가 트리에 있어야 빌드할 수 있다. 없는 센서는 `menuconfig` 를
아무리 찾아도 나오지 않는다. **먼저 트리에 있는지 확인**한다.

```bash
grep -rn "your,sensor-compatible" drivers/
```

### 「모듈로 빌드하면 언제든 넣고 뺄 수 있다」

빼려면 아무도 쓰고 있지 않아야 한다. 영상 장치처럼 열려 있는 파일이 있으면
`rmmod` 가 실패한다. 그리고 일부 드라이버는 **제거 경로가 제대로 구현돼 있지 않아**
뺐다 다시 넣으면 문제가 생긴다.

### 「`dmesg` 에 아무 것도 없으면 정상이다」

장치가 아예 인식되지 않으면 로그도 없다. 「오류가 없다」와
「시도조차 안 했다」는 다르다. **디바이스트리에 노드가 있는지**부터 확인한다.
→ [디바이스 트리](디바이스트리.md)

### 「최신 커널이 좋다」

임베디드 제품은 벤더 패치와 장기 지원 여부가 더 중요하다.
최신 메인라인으로 올리면 벤더 드라이버가 안 붙는 경우가 흔하고,
**보안 패치를 스스로 백포트해야 하는 부담**이 생긴다.

### 「커널 버전만 맞으면 모듈이 호환된다」

설정과 컴파일러까지 포함한 `vermagic` 이 맞아야 한다.
같은 `6.12.59` 라도 설정이 다르면 거부된다.
