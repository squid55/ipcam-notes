# 플래시 · 파일시스템 (MTD · UBI · UBIFS)

> 임베디드 기기의 저장장치는 대개 하드디스크도 SSD 도 아닌 생(raw) 플래시다.
> 그래서 `ext4` 를 그냥 얹을 수 없다.

## 왜 필요한가

펌웨어를 올리고, 설정을 저장하고, 로그를 쌓는 자리가 전부 여기다.
용량이 수십 MB 단위라 **몇 KB 단위로 아껴야 하는 상황이 실제로 온다.**

그리고 여기를 잘못 다루면 기기가 부팅하지 않는다. 되돌리려면 물리적으로
분해해서 프로그래머를 물려야 한다. 조심해야 하는 이유는 그것이다.

## 최소 이해 수준

- **플래시는 덮어쓸 수 없다.** 쓰기는 1→0 만 가능하고, 0→1 로 되돌리려면
  **블록 단위로 지워야** 한다. 그래서 「파일 수정」이 곧 「블록 지우고 다시 쓰기」다.
- **지우기 횟수에 수명이 있다.** 블록당 수만~수십만 회다.
  한 자리만 계속 쓰면 거기만 먼저 죽는다 → **웨어 레벨링**이 필요하다.
- **NOR 과 NAND 는 다르다.**

  | | NOR | NAND |
  |---|---|---|
  | 용량 | 작다 (수 MB~수십 MB) | 크다 (수백 MB~) |
  | 읽기 | 바이트 단위 임의 접근, 실행 가능(XIP) | 페이지 단위 |
  | 불량 블록 | 원칙적으로 없다 | 출하 시부터 있다 |
  | 쓰기 속도 | 느리다 | 빠르다 |
  | 쓰임 | 부트로더 · 작은 루트fs | 큰 루트fs · 저장 영역 |

- **MTD 가 추상화 계층이다.** `/dev/mtd0`, `/dev/mtdblock0`.
  파티션은 디바이스트리나 부트로더에서 정의한다.
- **UBI 는 MTD 위의 볼륨 관리자다.** 웨어 레벨링과 불량 블록 관리를 맡고,
  그 위에 논리 볼륨을 만든다. LVM 과 비슷한 자리다.
- **UBIFS 는 UBI 위의 파일시스템이다.** 로그 구조 · 압축 지원 · 전원 차단 내성.
- **읽기 전용 루트 + 쓰기 가능 데이터**로 나누는 것이 보통이다.
  루트는 `squashfs`(압축·읽기전용), 데이터는 UBIFS 또는 JFFS2.
- **`tmpfs` 를 적극적으로 쓴다.** `/tmp`·`/run` 을 플래시에 두면
  로그와 임시 파일이 수명을 갉아먹는다.

## 직접 해보기

### 1. 무엇이 어떻게 나뉘어 있는지

```bash
cat /proc/mtd
```
파티션 이름 · 크기 · 지우기 블록 크기가 나온다.

```bash
ubinfo -a
```
UBI 볼륨 목록과 각 볼륨의 LEB 개수 · 사용량이 나온다.

```bash
df -h
mount | grep -E 'ubifs|squashfs|jffs2|tmpfs'
```
어디가 읽기 전용이고 어디가 쓰기 가능한지 확인한다.

### 2. 남은 공간을 **쓰기 전에** 확인

```bash
df -h /대상경로
```

⚠ 이 한 줄을 건너뛰면 파일이 조용히 잘린 채 저장될 수 있다.
아래 오해 절을 본다.

### 3. 압축률 때문에 `df` 가 부정확한 것 확인

UBIFS 는 압축하므로 「남은 공간」이 추정치다.

```bash
df -h /데이터경로
# 실제로 큰 파일을 넣어 본다
dd if=/dev/urandom of=/데이터경로/t.bin bs=1M count=5
df -h /데이터경로
```

무작위 데이터는 압축이 안 되므로 표시된 여유가 그대로 줄어든다.
텍스트 파일이면 훨씬 덜 준다. **`df` 값을 보수적으로 읽어야 하는 이유다.**

```bash
rm /데이터경로/t.bin
```

### 4. 파티션 백업 뜨기

```bash
# 읽기
dd if=/dev/mtd3 of=/tmp/backup.bin bs=4096
md5sum /tmp/backup.bin
ls -l /tmp/backup.bin
```

**크기와 해시를 둘 다 기록해 둔다.** 나중에 이것 하나로 되돌릴 수 있다.

### 5. 쓰기 전 확인 절차

플래시에 쓰는 작업은 되돌리기가 어렵다. 최소 세 가지를 확인하고 진행한다.

```
① 백업이 정말 떠졌는가        — 크기가 0 이 아니고 예상 크기와 맞는가
② 쓸 이미지가 온전한가        — md5 가 빌드 산출물의 값과 같은가
③ 전송이 다 끝났는가          — 전송한 바이트 수가 이미지 크기와 같은가
```

셋 중 하나라도 확인하지 않으면 「반쯤 쓰인 플래시」가 될 수 있다.
실측: 이 절차를 지키지 않아 데이터 영역을 통째로 잃은 일이 있었다.

## 더 들어가면

- **가비지 컬렉션.** UBIFS 는 로그 구조라 지운 공간이 즉시 돌아오지 않는다.
  파일을 지워도 `df` 가 바로 줄지 않을 수 있다.
  실측: 지운 뒤 한참 지나서야 사용량이 떨어지는 것을 확인했다.
- **원자적 갱신.** 설정 파일을 안전하게 바꾸려면
  `임시 파일에 쓰기 → fsync → rename` 이다. `rename` 은 원자적이다.
  덮어쓰는 도중 전원이 나가면 파일이 반쯤 남는다.
- **A/B 파티션.** 두 벌을 두고 번갈아 쓴다. 실패 시 이전 것으로 부팅한다.
  용량이 두 배 필요해서 작은 NOR 에서는 쓰기 어렵다.
  → [무결성과 서명 업데이트](../보안/무결성과서명업데이트.md)
- **`ubiattach` / `ubimkvol` / `ubiupdatevol`** — 볼륨을 만들고 갱신하는 도구.
  운영 중 볼륨 갱신은 `ubiupdatevol` 이 원자적으로 처리한다.
- **`mtd-utils`** — `flash_erase` · `nandwrite` · `nanddump`.
  불량 블록을 건너뛰는지 여부가 도구마다 다르다.
- **eMMC 는 다른 세계다.** 컨트롤러가 웨어 레벨링을 내부에서 하므로
  `ext4` 를 그냥 쓴다. 대신 그 컨트롤러를 들여다볼 수 없다.

## 흔한 오해

### 「남은 공간이 부족하면 오류가 난다」

항상 그렇지는 않다. 실측: 여유가 모자란 상태에서 압축 파일을 풀었더니
**오류 없이 마지막 파일이 잘린 채** 저장됐다. 실행 파일이었고, 부팅 후에야
실행되지 않아서 알게 됐다.

그래서 규칙을 하나 만들었다 — **크기가 큰 것 여러 개를 한 번에 풀지 않는다.**
여유를 먼저 확인하고, 애매하면 이미지를 다시 빌드해 통째로 쓴다.

### 「이미지 해시가 다르면 내용이 다르다」

파일시스템 이미지는 그렇지 않을 수 있다. UBIFS·squashfs 이미지는
압축 결과와 노드 배치가 빌드마다 달라져서 **내용이 같아도 바이트가 다르다.**

실측: 같은 소스로 만든 두 이미지의 크기와 md5 가 달라 「정체불명의 변경분」을
의심했는데, **파일 단위로 해시를 대조하니 차이가 0 건**이었다.
컨테이너의 비결정성이었지 내용 차이가 아니었다.

⇒ 재현성을 보일 때는 「이미지 바이트가 같다」가 아니라
**「모든 파일이 소스에서 재현되고 파일별 해시가 일치한다」**로 보이는 편이 맞다.
바이트 단위 재현이 필요하면 `SOURCE_DATE_EPOCH` 와 압축 옵션 고정을
별도 과제로 잡는다.

### 「파일을 지웠으니 복구할 수 없다」

로그 구조 파일시스템은 지운 데이터가 GC 전까지 물리적으로 남아 있다.
민감한 값을 지울 때는 그 점을 고려해야 한다. 플래시에서 `shred` 는
**웨어 레벨링 때문에 의도대로 동작하지 않는다.**

### 「루트 파일시스템을 쓰기 가능하게 두면 편하다」

편하지만 전원 차단 때 깨질 위험이 늘고, 변조 탐지도 어려워진다.
읽기 전용으로 두고 필요한 곳만 쓰기 가능한 볼륨으로 분리하는 편이 낫다.

### 「부트로더 파티션은 건드릴 일이 없다」

건드릴 일은 없지만, 잘못 겨냥한 `dd` 한 번이면 지워진다.
**파티션 번호는 매번 `/proc/mtd` 로 확인**하고, 이름으로 확인할 수 있으면 그렇게 한다.
