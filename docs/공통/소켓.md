# 소켓 · TCP / UDP

> 네트워크로 데이터를 주고받는 기본 인터페이스.
> 위의 모든 프로토콜(HTTP · RTSP · RTP)이 이 위에 얹힌다.

## 왜 필요한가

IP카메라는 네트워크 장치다. 모든 기능이 소켓을 지나간다.
그래서 「연결이 안 된다」 · 「끊긴다」 · 「느리다」의 원인을 이 계층에서
확인할 수 있어야 한다.

그리고 TCP 와 UDP 의 차이가 곧 **RTSP/TCP 와 RTP/UDP 의 차이**다.
왜 실시간 영상이 UDP 를 쓰는지가 여기서 설명된다.

## 최소 이해 수준

- **TCP 와 UDP.**

  | | TCP | UDP |
  |---|---|---|
  | 연결 | 있다 (3-way handshake) | 없다 |
  | 순서 보장 | 있다 | 없다 |
  | 재전송 | 한다 | 안 한다 |
  | 경계 | **없다 (바이트 스트림)** | 있다 (데이터그램) |
  | 지연 | 유실 시 크게 는다 | 일정하다 |
  | 쓰는 곳 | 제어 · 설정 · 파일 | 실시간 미디어 |

- **TCP 는 경계가 없다.** `write` 를 3번 해도 상대는 1번에 받을 수 있다.
  **그래서 프로토콜이 길이나 구분자를 스스로 정의해야 한다.**
  HTTP 는 `\r\n\r\n` 과 `Content-Length` 로 해결한다.
- **소켓 호출 순서.**
  ```
  서버: socket → bind → listen → accept → read/write → close
  클라: socket → connect → write/read → close
  UDP:  socket → (bind) → sendto/recvfrom → close
  ```
- **`SO_REUSEADDR` 을 쓴다.** 없으면 서버를 재시작할 때
  `bind: Address already in use` 가 난다(`TIME_WAIT` 때문).
- **`TCP_NODELAY`.** Nagle 알고리즘을 끈다. 작은 메시지를 모아 보내지 않게 해서
  **제어 명령의 지연을 줄인다.** 대량 전송에는 켜 두는 편이 낫다.
- **부분 읽기·쓰기를 처리한다.** `read`/`write` 는 요청한 만큼 처리하지 않을 수 있다.
  ```c
  ssize_t write_all(int fd, const void *b, size_t n) {
      const char *p = b; size_t left = n;
      while (left) {
          ssize_t k = write(fd, p, left);
          if (k < 0) { if (errno == EINTR) continue; return -1; }
          p += k; left -= k;
      }
      return n;
  }
  ```
  **이 함수 없이 쓴 코드는 느린 네트워크에서 데이터가 잘린다.**
- **`SIGPIPE` 를 막는다.** 끊긴 소켓에 쓰면 프로세스가 죽는다.
  → [비동기 I/O](../리눅스/비동기IO.md)
- **바이트 순서.** 네트워크는 빅 엔디안이다. `htons`·`htonl`·`ntohs`·`ntohl`.
  **RISC-V·ARM 은 리틀 엔디안**이라 변환이 필요하다.
- **UDP 크기 제한.** MTU(보통 1500)를 넘으면 IP 단편화가 일어나고,
  **조각 하나만 잃어도 전체를 잃는다.** 그래서 RTP 는 1400바이트쯤으로 쪼갠다.
  → [RTP · RTCP](../네트워크/RTP.md)
- **타임아웃을 반드시 둔다.** 기본값은 사실상 무한이다.
  ```c
  struct timeval tv = { .tv_sec = 5 };
  setsockopt(fd, SOL_SOCKET, SO_RCVTIMEO, &tv, sizeof tv);
  ```

## 직접 해보기

### 1. 무엇이 열려 있는지

```bash
ss -tlnp                             # TCP 대기 중
ss -ulnp                             # UDP
ss -tnp state established            # 연결된 것
```

**제품 점검에서 이것이 첫 단계다.** 열려 있어야 할 포트만 열려 있는지 본다.
→ [인증과 인가](../보안/인증과인가.md)

### 2. 밖에서 스캔해 보기

```bash
nmap -Pn -p- <카메라 IP>
nmap -sU -p 3702,123,1900 <카메라 IP>       # UDP 는 따로
```

**안에서 본 `ss` 와 밖에서 본 결과가 다르면** 방화벽이 있는 것이다.

### 3. 연결이 되는지만 확인

```bash
nc -vz <주소> 443
timeout 3 bash -c 'cat < /dev/tcp/<주소>/443' && echo 열림
```

거부(`Connection refused`)와 무응답(타임아웃)은 다르다.
**거부는 그 호스트에 서비스가 없는 것, 무응답은 방화벽이 버리는 것**이다.

### 4. 최소 TCP 서버·클라이언트 만들어 보기

```c
/* 서버 */
#include <sys/socket.h>
#include <netinet/in.h>
#include <netinet/tcp.h>
#include <unistd.h>
#include <string.h>
#include <stdio.h>
#include <signal.h>

int main(void) {
    signal(SIGPIPE, SIG_IGN);
    int ls = socket(AF_INET, SOCK_STREAM, 0);
    int on = 1;
    setsockopt(ls, SOL_SOCKET, SO_REUSEADDR, &on, sizeof on);
    struct sockaddr_in a = { .sin_family = AF_INET, .sin_port = htons(9000),
                             .sin_addr.s_addr = htonl(INADDR_ANY) };
    if (bind(ls, (struct sockaddr*)&a, sizeof a) < 0) { perror("bind"); return 1; }
    listen(ls, 16);
    for (;;) {
        int c = accept(ls, NULL, NULL);
        if (c < 0) { perror("accept"); continue; }
        setsockopt(c, IPPROTO_TCP, TCP_NODELAY, &on, sizeof on);
        char buf[512];
        ssize_t n = read(c, buf, sizeof buf);
        if (n > 0) write(c, buf, n);
        close(c);
    }
}
```

```bash
gcc s.c -o s && ./s &
printf 'hello\n' | nc localhost 9000
```

### 5. TCP 핸드셰이크를 눈으로 보기

```bash
sudo tcpdump -i any -n 'tcp port 9000' -c 10
```

```
SYN → SYN-ACK → ACK      연결
FIN → ACK → FIN → ACK    종료
RST                       거부 또는 강제 종료
```

**`RST` 가 보이면 정상 종료가 아니다.** 상대가 거부했거나 소켓을 강제로 닫았다.

### 6. UDP 유실을 재보기

```bash
# 받는 쪽
nc -u -l 9001 | wc -l &
# 보내는 쪽 (1000줄)
seq 1 1000 | nc -u localhost 9001
```

같은 기기에서는 대개 다 온다. **네트워크를 건너면 줄어든다.**
의도적으로 유실을 만들어 시험할 수도 있다.

```bash
sudo tc qdisc add dev <인터페이스> root netem loss 5% delay 50ms
# 되돌리기
sudo tc qdisc del dev <인터페이스> root
```

⚠ 본인 장비에서만 한다. **관리 접속이 끊길 수 있으니** 콘솔 접근 수단을 확보하고 한다.

### 7. 실제로 무엇이 오가는지 보기

```bash
sudo tcpdump -i any -n -A 'tcp port 554' -c 40        # RTSP 는 텍스트다
sudo tcpdump -i any -n -s0 -w /tmp/c.pcap host <카메라 IP>
tshark -r /tmp/c.pcap -q -z conv,tcp
```

암호화된 트래픽은 내용을 볼 수 없다. **핸드셰이크와 패킷 흐름만** 보인다.
→ [TLS · X.509](../보안/TLS-X509.md)

### 8. 버퍼와 혼잡 상태 보기

```bash
ss -tim state established '( dport = :554 or sport = :554 )'
```

`rtt` · `cwnd` · `retrans` 가 나온다.
**`retrans` 가 크면 유실이 있고, TCP 가 재전송하느라 지연이 커진 것**이다.

## 더 들어가면

- **`TIME_WAIT`.** 연결을 닫은 쪽이 2×MSL 동안 남긴다.
  짧은 연결을 많이 만들면 쌓인다. **연결을 재사용하는 설계**가 근본 해결이다.
- **Keepalive.** 조용한 연결이 살아 있는지 확인한다.
  ```c
  setsockopt(fd, SOL_SOCKET, SO_KEEPALIVE, &on, sizeof on);
  /* TCP_KEEPIDLE · TCP_KEEPINTVL · TCP_KEEPCNT 로 주기 조절 */
  ```
  **NAT 나 방화벽이 조용한 연결을 끊는 것**을 막는 데도 쓴다.
- **혼잡 제어.** 유실을 신호로 보고 전송 속도를 줄인다.
  **그래서 TCP 로 영상을 보내면 회선이 나쁠 때 지연이 쌓인다.**
- **멀티캐스트.** 한 번 보내 여러 수신자가 받는다.
  감시 시스템에서 대역폭을 크게 아낄 수 있지만 **스위치·라우터 설정(IGMP)이 필요**하다.
- **`SO_REUSEPORT`.** 여러 프로세스가 같은 포트를 나눠 받는다.
  커널이 연결을 분배한다.
- **IPv6.** `AF_INET6` 과 `sockaddr_in6`. 주소 계열에 중립적으로 쓰려면
  `getaddrinfo` 를 쓰고 `sockaddr_storage` 로 받는다.
- **유닉스 도메인 소켓.** 같은 기기 안의 프로세스 사이 통신.
  네트워크를 거치지 않아 빠르고, **파일 권한으로 접근을 제어**할 수 있다.
  그리고 fd 자체를 넘길 수 있어 DMABUF 전달에 쓰인다.

## 흔한 오해

### 「TCP 는 신뢰할 수 있으니 실시간에도 좋다」

신뢰성의 대가가 지연이다. 유실이 생기면 재전송을 기다리는 동안
**뒤의 데이터가 다 막힌다**(head-of-line blocking).
3초 늦게 도착한 영상 프레임은 이미 쓸모가 없다.

### 「`write` 가 성공했으니 상대가 받았다」

커널 버퍼에 들어갔다는 뜻이다. 상대가 받았는지는 알 수 없다.
**애플리케이션 수준 확인 응답**이 필요하면 프로토콜에 넣어야 한다.

### 「연결이 끊기면 `read` 가 오류를 낸다」

정상 종료면 `read` 가 `0` 을 돌린다. 오류가 아니다.
그리고 **케이블이 뽑힌 경우는 아무 일도 일어나지 않는다** —
keepalive 나 애플리케이션 타임아웃이 없으면 영원히 기다린다.

### 「UDP 는 순서가 없으니 쓸 수 없다」

응용이 순번을 넣으면 된다. RTP 가 정확히 그것을 한다.
**「무엇을 보장할지 응용이 고른다」**는 것이 UDP 의 이점이다.

### 「포트가 열려 있으면 서비스가 동작한다」

`ss` 에 보이는 것은 프로세스가 `listen` 했다는 뜻이다.
그 프로세스가 멈춰 있으면 연결은 되고 응답은 없다.
**실제 요청을 보내 확인**해야 한다.

### 「같은 서브넷이면 통신된다」

서브넷 마스크 · 게이트웨이 · ARP · 방화벽이 각각 막을 수 있다.
그리고 **주소를 잘못 알고 있는 경우가 의외로 많다.**

실측: 웹 로그인이 계속 실패해서 백엔드를 뒤졌는데,
원인은 **브라우저가 캐시된 옛 IP 로 요청**하고 있던 것이었다.
같은 요청을 올바른 주소로 `curl` 하면 정상이었다.
DHCP 로 주소가 바뀌는 환경에서 특히 자주 생긴다.

```bash
# 실제 주소를 먼저 확인한다
ip -4 addr show
arp -an | grep <MAC 앞자리>
```
