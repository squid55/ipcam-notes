# 자료구조 · 알고리즘

> 데이터를 어떻게 담고 어떻게 찾을지의 선택.
> 임베디드에서는 「빠른가」보다 **「메모리를 얼마나 쓰는가」**가 먼저 걸린다.

## 왜 필요한가

영상 파이프라인의 자료구조는 대개 셋이다 —
프레임 큐 · 세션 표 · 링 버퍼. 이 셋을 제대로 고르면 나머지는 따라온다.

그리고 임베디드에서는 **할당 자체가 위험**하다.
프레임마다 `malloc` 하면 단편화가 쌓여 며칠 뒤에 실패한다.
그래서 미리 잡아 두고 재사용하는 구조가 표준이 된다.

## 최소 이해 수준

- **복잡도 표기.** `O(1)` · `O(log n)` · `O(n)` · `O(n log n)` · `O(n²)`.
  **입력이 커질 때의 증가율**이고, 작은 n 에서는 상수가 더 중요하다.
- **자주 쓰는 것들.**

  | 구조 | 조회 | 삽입/삭제 | 쓰는 곳 |
  |---|---|---|---|
  | 배열 | `O(1)` 색인 | 끝에 `O(1)`, 중간 `O(n)` | 고정 크기 버퍼 풀 |
  | 링 버퍼 | `O(1)` | `O(1)` | **프레임 큐 · 로그 버퍼** |
  | 연결 리스트 | `O(n)` | `O(1)` (위치를 알면) | 커널 자료구조 (`list_head`) |
  | 해시 표 | 평균 `O(1)` | 평균 `O(1)` | 세션 표 · 연결 관리 |
  | 이진 탐색 트리 | `O(log n)` | `O(log n)` | 정렬 순회가 필요할 때 |
  | 힙 (우선순위 큐) | 최소 `O(1)` | `O(log n)` | 타이머 · 스케줄 |

- **링 버퍼가 이 분야의 핵심 구조다.** 고정 크기 배열에 읽기·쓰기 색인 두 개.
  ```c
  typedef struct { uint8_t *buf; size_t cap, head, tail; } ring_t;

  static inline size_t ring_used(const ring_t *r) {
      return (r->head - r->tail) % r->cap;     /* cap 은 2의 거듭제곱이면 더 싸다 */
  }
  ```
  **할당이 한 번뿐**이고, 오래된 데이터를 자연스럽게 덮어쓴다.
- **캐시가 복잡도보다 중요한 경우가 많다.**
  연결 리스트는 이론상 삽입이 `O(1)` 이지만 메모리가 흩어져 있어
  순회할 때 배열보다 훨씬 느리다. **연속 메모리를 선호한다.**
- **정렬과 탐색은 표준 라이브러리를 쓴다.**
  ```c
  qsort(a, n, sizeof a[0], cmp);
  void *p = bsearch(&key, a, n, sizeof a[0], cmp);
  ```
  ```cpp
  std::sort(v.begin(), v.end());
  auto it = std::lower_bound(v.begin(), v.end(), key);
  ```
  **직접 구현할 이유가 거의 없다.**
- **이분 탐색은 알고리즘이 아니라 습관이다.** 정렬된 데이터뿐 아니라
  **버그 위치 찾기 · 커밋 찾기 · 설정값 한계 찾기**에 쓴다.
  → [디버깅](디버깅.md)
- **해시의 주의점.** 최악은 `O(n)` 이다. 그리고 공격자가 키를 고를 수 있으면
  일부러 충돌을 만들 수 있다(해시 충돌 DoS).
  **외부 입력을 키로 쓰는 표는 무작위 시드를 섞는다.**
- **메모리 풀.** 고정 크기 블록을 미리 잡아 두고 빌려주고 돌려받는다.
  ```
  장점: 할당 시간이 일정하다 · 단편화가 없다 · 상한이 보장된다
  단점: 최대 사용량만큼 미리 잡아야 한다
  ```
  **실시간 시스템에서는 사실상 필수**다.

## 직접 해보기

### 1. 링 버퍼 만들어 보기

```c
#include <stdint.h>
#include <stdlib.h>
#include <string.h>
#include <stdio.h>

typedef struct { uint8_t *b; size_t cap, head, tail; } ring_t;

static int  ring_init(ring_t *r, size_t cap) {
    r->b = malloc(cap); r->cap = cap; r->head = r->tail = 0;
    return r->b ? 0 : -1;
}
static size_t ring_used(ring_t *r)  { return (r->head - r->tail) % r->cap; }
static size_t ring_free_(ring_t *r) { return r->cap - 1 - ring_used(r); }

static size_t ring_write(ring_t *r, const uint8_t *s, size_t n) {
    if (n > ring_free_(r)) n = ring_free_(r);            /* 넘치면 잘라 쓴다 */
    for (size_t i = 0; i < n; i++) { r->b[r->head] = s[i]; r->head = (r->head+1) % r->cap; }
    return n;
}
static size_t ring_read(ring_t *r, uint8_t *d, size_t n) {
    if (n > ring_used(r)) n = ring_used(r);
    for (size_t i = 0; i < n; i++) { d[i] = r->b[r->tail]; r->tail = (r->tail+1) % r->cap; }
    return n;
}

int main(void) {
    ring_t r; ring_init(&r, 8);
    printf("쓴 바이트 %zu (용량 8)\n", ring_write(&r, (uint8_t*)"abcdefghij", 10));
    uint8_t out[16] = {0};
    printf("읽은 바이트 %zu: %s\n", ring_read(&r, out, 16), out);
    free(r.b);
}
```

```bash
gcc -Wall -Wextra ring.c -o ring && ./ring
```

**용량이 8인데 7만 들어간다.** 한 칸을 비워 두어 「가득 찼음」과 「비었음」을
구분하는 것이 흔한 기법이다.

### 2. 한계 상황을 시험하기

```
① 가득 찬 상태에서 쓰면 어떻게 되는가   → 자르는가, 오래된 것을 버리는가
② 빈 상태에서 읽으면 어떻게 되는가
③ 색인이 감싸는 지점(head < tail)에서 정상인가
```

**③이 버그의 단골 자리다.** 경계에서 한 바퀴 돌려 보는 시험을 꼭 넣는다.

### 3. 복잡도보다 캐시가 중요한 것 보기

```cpp
#include <vector>
#include <list>
#include <chrono>
#include <cstdio>
int main() {
    const int N = 2'000'000;
    std::vector<int> v(N, 1);
    std::list<int>   l(N, 1);

    auto t = std::chrono::steady_clock::now();
    long sv = 0; for (int x : v) sv += x;
    auto d1 = std::chrono::steady_clock::now() - t;

    t = std::chrono::steady_clock::now();
    long sl = 0; for (int x : l) sl += x;
    auto d2 = std::chrono::steady_clock::now() - t;

    printf("vector %lld us\nlist   %lld us\n",
        (long long)std::chrono::duration_cast<std::chrono::microseconds>(d1).count(),
        (long long)std::chrono::duration_cast<std::chrono::microseconds>(d2).count());
    (void)sv; (void)sl;
}
```

둘 다 `O(n)` 순회인데 **몇 배 차이가 난다.**

### 4. 메모리 풀 효과 재기

```c
/* 매번 할당 */
for (int i = 0; i < 100000; i++) { void *p = malloc(4096); free(p); }

/* 풀 재사용 */
void *pool[64]; for (int i=0;i<64;i++) pool[i]=malloc(4096);
for (int i = 0; i < 100000; i++) { void *p = pool[i % 64]; (void)p; }
```

시간 차이도 있지만, **장시간 돌렸을 때 단편화 차이**가 더 크다.

```bash
# 단편화 관찰

cat /proc/buddyinfo | head -3
```

### 5. 프레임 큐 정책을 비교해 보기

같은 큐에 세 정책을 넣어 보고 지연을 재본다.

```
① 무한 큐          → 메모리가 늘고 지연이 쌓인다
② 가득 차면 막는다  → 캡처가 멈춰 프레임을 놓친다
③ 가득 차면 가장 오래된 것을 버린다  → 지연이 일정하다  ← 실시간 영상의 답
```

→ [멀티스레드](../리눅스/멀티스레드.md)

### 6. 세션 표를 해시로

```c
/* 세션 ID 문자열 → 세션 구조체 */
static unsigned hash_str(const char *s, unsigned seed) {
    unsigned h = seed;                      /* 시드를 무작위로 두면 충돌 공격 완화 */
    for (; *s; s++) h = h * 131u + (unsigned char)*s;
    return h;
}
```

**세션 수의 상한을 정해 두어야** 한다. 무제한이면 접속 폭주로 메모리가 고갈된다.
→ [인증과 인가](../보안/인증과인가.md)

## 더 들어가면

- **락 프리 링 버퍼.** 생산자 하나 · 소비자 하나(SPSC)라면 잠금 없이 가능하다.
  `head` 는 생산자만, `tail` 은 소비자만 쓰면 된다. 메모리 순서를 정확히 다뤄야 한다.
- **2의 거듭제곱 용량.** `% cap` 을 `& (cap-1)` 로 바꿀 수 있어 나눗셈이 사라진다.
  임베디드에서 유의미한 최적화다.
- **슬랩 할당자.** 커널이 같은 크기 객체를 효율적으로 관리하는 방식.
  ```bash
  cat /proc/slabinfo | head -5
  ```
- **B-트리와 지역성.** 디스크·플래시에서는 한 번에 읽는 단위가 크므로
  이진 트리보다 분기 수가 많은 트리가 유리하다.
- **문자열 처리.** 파싱이 많은 코드(HTTP · RTSP 헤더)는
  복사하지 않고 구간만 가리키는 방식이 빠르다.
  C++ 이면 `std::string_view`. **원본보다 오래 살면 안 된다.**
- **알고리즘이 필요한 실제 자리.** 영상 분석의 IoU 매칭(이분 매칭),
  타임라인 검색(이분 탐색), 녹화 보존 정책(우선순위 큐).
  → [Video Analytics](../관제/VideoAnalytics.md)

## 흔한 오해

### 「복잡도가 낮으면 빠르다」

n 이 작으면 상수가 지배한다. 연결 리스트가 배열을 이기는 경우는
**요소가 아주 크고 이동 비용이 클 때**뿐이다.
카메라 채널 32개 같은 규모에서는 배열 선형 탐색이 해시보다 빠를 수 있다.

### 「메모리는 필요할 때 할당하면 된다」

임베디드에서는 실패할 수 있고, 단편화가 쌓인다.
그리고 **할당 시간이 일정하지 않아** 실시간 경로에서 지연이 튄다.
프레임 경로에서는 미리 잡는다.

### 「큐는 크게 잡으면 안전하다」

큐가 크면 지연이 커진다. 30fps 에서 큐가 90장이면
**3초 늦은 영상**을 보게 된다. 실시간 감시에서는 큐를 짧게 두고 버린다.

### 「해시는 항상 `O(1)` 이다」

충돌이 몰리면 `O(n)` 이 된다. 외부에서 키를 고를 수 있는 경우
의도적으로 그렇게 만들 수 있으므로 **시드 무작위화**가 필요하다.

### 「직접 구현하면 더 빠르다」

표준 라이브러리의 `sort` 는 수십 년 다듬어진 것이다.
직접 쓴 정렬이 이길 확률은 낮고, **버그가 들어갈 확률은 높다.**
구조가 특수해서 표준이 안 맞을 때만 직접 쓴다.

### 「자료구조를 고르는 것은 나중 문제다」

프레임 경로의 구조는 나중에 바꾸기 어렵다.
**큐에 무엇을 넣는지**(버퍼 자체인가, 핸들인가)가 복사 비용을 결정하고,
그것을 바꾸려면 파이프라인 전체를 고쳐야 한다.
