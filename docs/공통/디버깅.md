# 디버깅 (gdb · 로그 · 이분 탐색)

> 문제의 원인을 찾는 일. 도구를 많이 아는 것보다
> **범위를 반으로 줄이는 순서를 아는 것**이 핵심이다.

## 왜 필요한가

임베디드 영상 시스템은 계층이 많다 —
센서 · CSI · ISP · 인코더 · 커널 · 응용 · 네트워크 · 브라우저.
**어느 계층인지 모르면 8개를 다 뒤지게 된다.**

그리고 여기서는 「재현되지 않는 문제」가 흔하다.
그 경우 추측으로는 절대 답이 안 나온다.

## 최소 이해 수준

- **순서가 있다.** 도구보다 이것이 먼저다.
  ```
  ① 현상을 정확히 적는다 — 언제 · 무엇을 하면 · 어떻게 되는가
  ② 재현 절차를 만든다  — 없으면 고쳤는지 확인할 수 없다
  ③ 범위를 반으로 자른다 — 계층 경계마다 확인 지점을 둔다
  ④ 한 번에 하나만 바꾼다
  ⑤ 고친 뒤 ②로 확인한다
  ```
- **③이 가장 중요하다.** 8개 계층을 순서대로 뒤지면 8번이고,
  절반으로 자르면 3번이다. **중간 지점에서 데이터가 정상인지 확인**한다.
- **이분 탐색은 시간에도 쓴다.** 「어제는 됐는데 오늘 안 된다」면
  커밋을 반으로 자른다. `git bisect` 가 이것을 자동화한다.
- **로그의 기본.** 시각 · 위치 · 값. 셋 중 하나라도 빠지면 쓸모가 줄어든다.
  ```
  [12:34:56.789] encoder.c:142 qbuf 실패 index=2 errno=16(EBUSY)
  ```
  **`errno` 를 숫자와 이름으로 함께 남긴다.** 숫자만 있으면 매번 찾아봐야 한다.
- **로그 레벨을 나눈다.** 평소에는 `info` 까지, 문제가 날 때 `debug` 를 켠다.
  **런타임에 레벨을 바꿀 수 있게** 만드는 것이 실전에서 크게 유용하다.
- **`gdb` 의 최소 사용법.**
  ```
  gdb ./prog            실행 파일로 시작
  run / r               실행
  bt                    호출 스택 (가장 많이 쓴다)
  break file.c:42       중단점
  print x / p x         값 보기
  continue / c          계속
  info threads          스레드 목록
  thread apply all bt   전체 스레드 스택
  ```
- **코어 덤프를 켠다.** 죽은 뒤에 원인을 볼 수 있다.
  ```bash
  ulimit -c unlimited
  cat /proc/sys/kernel/core_pattern
  ```
- **도구는 계층별로 다르다.**

  | 계층 | 도구 |
  |---|---|
  | 응용 논리 | `gdb` · 로그 · 단위 시험 |
  | 메모리 오류 | `-fsanitize=address` · `valgrind` |
  | 경쟁 조건 | `-fsanitize=thread` · `helgrind` |
  | 시스템 콜 경계 | `strace` · `ltrace` |
  | 커널 · 드라이버 | `dmesg` · `ftrace` · 동적 디버그 |
  | 네트워크 | `tcpdump` · `tshark` |
  | 전기 신호 | 오실로스코프 · 로직 애널라이저 |

## 직접 해보기

### 1. 죽은 프로그램의 원인 찾기

```bash
ulimit -c unlimited
./prog                              # 죽는다
coredumpctl list | tail -3
coredumpctl gdb                     # 또는: gdb ./prog core
```

```
(gdb) bt
(gdb) frame 2
(gdb) info locals
```

**`bt` 한 번으로 대부분 끝난다.** 어느 줄에서 어떤 값으로 죽었는지 나온다.

⚠ `-g` 로 빌드하지 않으면 줄 번호가 안 나온다.
**릴리스 빌드에도 `-g` 를 넣고 심볼만 따로 보관**하는 편이 낫다.

```bash
gcc -O2 -g prog.c -o prog
objcopy --only-keep-debug prog prog.debug
strip --strip-debug prog
```

### 2. 멈춘 프로그램 들여다보기

```bash
gdb -p $(pgrep myapp) -batch -ex 'thread apply all bt' 2>/dev/null | head -60
```

프로그램을 멈추지 않고도 스택을 볼 수 있다.
**교착이나 무한 루프의 위치가 바로 나온다.**

### 3. 메모리 오류 잡기

```bash
gcc -g -fsanitize=address,undefined prog.c -o prog_a && ./prog_a
```

```bash
valgrind --leak-check=full --track-origins=yes ./prog 2>&1 | tail -30
```

⚠ 두 도구를 **동시에 쓸 수 없다.** 그리고 `address` 와 `thread` 도 함께 못 쓴다.

### 4. 어디까지 갔는지 확인 (`strace`)

```bash
strace -f -tt -e trace=openat,ioctl,connect ./prog 2>&1 | tail -40
```

시스템 콜이 실패했으면 **원인이 커널 쪽**이고, 호출조차 없으면
그 코드에 도달하지 못한 것이다. 범위가 즉시 절반으로 줄어든다.

### 5. `git bisect` 로 언제 깨졌는지 찾기

```bash
git bisect start
git bisect bad                      # 현재는 깨졌다
git bisect good <잘 되던 커밋>
# 시험하고
git bisect good    # 또는 bad
# 반복하면 범인 커밋이 나온다
git bisect reset
```

자동화도 된다.

```bash
git bisect run ./scripts/test.sh    # 0=good, 1=bad
```

커밋 100개면 7번만 시험한다. → [Git](Git.md)

### 6. 로그를 나중에 켤 수 있게 만들기

```c
static int g_level = 1;             /* 0=err 1=info 2=debug */
#define LOGD(...) do { if (g_level >= 2) log_line("DBG", __FILE__, __LINE__, __VA_ARGS__); } while (0)
```

환경변수나 신호로 바꾸게 하면 **재배포 없이 로그를 올릴 수 있다.**

```bash
LOG_LEVEL=2 ./prog
kill -USR1 <PID>                    # 레벨 토글
```

### 7. 계층 경계에서 확인 지점 만들기

영상 문제라면 이 순서로 자른다.

```
① 센서에서 프레임이 오는가        v4l2-ctl --stream-count=1
② 인코더가 바이트를 내는가        파일로 저장해 크기 확인
③ 네트워크로 나가는가             tcpdump 로 패킷 수
④ 클라이언트가 받는가             ffplay 로 재생
⑤ 브라우저가 표시하는가           개발자 도구 네트워크 탭
```

**①이 실패하면 ②~⑤를 볼 이유가 없다.**
경계마다 「여기까지는 정상」을 확정하는 것이 요령이다.
→ [MIPI CSI-2](../영상/MIPI-CSI2.md)

### 8. 브라우저 쪽을 의심할 때

캐시가 원인인 경우가 많다.

```bash
# 서버가 실제로 무엇을 주는지 확인
curl -sk https://<주소>/viewer.js | md5sum
curl -skI https://<주소>/viewer.js | grep -i -E 'cache|etag|last-modified'
```

**서버 파일의 해시와 대조**하면 「서버가 옛것을 주는가」와
「브라우저가 옛것을 쓰는가」가 갈린다.

## 더 들어가면

- **`rr` (record and replay).** 실행을 기록해 뒤로 돌려가며 디버깅한다.
  재현이 어려운 버그에 강력하다.
- **`perf`.** 성능 병목 찾기.
  ```bash
  perf top -p <PID>
  perf record -g ./prog && perf report
  ```
- **동적 디버그 (커널).** 재빌드 없이 드라이버 로그를 켠다.
  ```bash
  echo 'file drivers/media/i2c/foo.c +p' | sudo tee /sys/kernel/debug/dynamic_debug/control
  ```
  → [디바이스 드라이버](../BSP/디바이스드라이버.md)
- **원격 디버깅.** 보드에 `gdbserver` 를 올리고 호스트의 `gdb` 로 붙는다.
  ```bash
  # 보드
  gdbserver :2345 ./prog
  # 호스트
  gdb-multiarch ./prog -ex 'target remote <보드IP>:2345'
  ```
  → [크로스 컴파일](../BSP/크로스컴파일.md)
- **어서션.** 「있을 수 없는 상태」를 코드에 적어 둔다.
  조용히 잘못된 값으로 계속 도는 것보다 **그 자리에서 멈추는 것**이 낫다.
  다만 제품에서 프로세스를 죽일지는 따로 판단한다.
- **관측 가능성.** 사후 디버깅이 아니라 **평소에 상태를 노출**해 둔다.
  프레임 수 · 유실 수 · 큐 길이 · 재연결 횟수를 셈해서 조회할 수 있게 만든다.

## 흔한 오해

### 「증상이 있는 곳이 원인이 있는 곳이다」

영상이 깨지면 인코더를 의심하게 되지만, 원인이 센서 입력일 수 있다.
**증상은 가장 바깥에서 나타난다.** 안쪽부터 확인하는 순서를 지킨다.

### 「로그를 많이 남기면 도움이 된다」

너무 많으면 중요한 줄이 묻히고, 기록 자체가 부하가 된다.
그리고 주기 검사 결과를 매번 남기면 **실패 기록이 파묻힌다.**
실패할 때와 복구할 때만 남기는 편이 실용적이다.
→ [감사기록](../보안/감사기록.md)

### 「재현이 안 되니 고칠 수 없다」

재현 절차를 만드는 것 자체가 작업이다. 부하를 올리거나 지연을 넣거나
타이밍을 바꿔 확률을 올린다. `-fsanitize=thread` 처럼
**재현 없이 잡아 주는 도구**도 있다.

### 「고쳤으니 끝이다」

같은 원인으로 다른 곳도 깨져 있을 수 있다.
그리고 **왜 시험에서 못 잡혔는지**를 봐야 다음에 막을 수 있다.
고친 뒤 그 상황을 시험으로 남긴다.

### 「릴리스 빌드는 디버깅할 수 없다」

`-g` 를 넣어도 최적화에 영향이 없다. 심볼을 분리해 보관하면
**크기도 늘지 않고 나중에 스택을 읽을 수 있다.**
이것을 안 해 두면 현장에서 받은 코어 덤프가 쓸모없어진다.

### 「배포 절차는 디버깅과 무관하다」

배포가 원인이 되는 경우가 있다. 실측: 데몬을 죽이고 손으로 다시 띄웠는데
감시 스크립트도 되살려서 **같은 데몬이 두 개** 돌았다.
증상은 데이터 손상이었고 코드에는 문제가 없었다.
**「어떻게 배포했는가」도 재현 절차에 포함**시켜야 한다.
