# WebRTC — 왜 빠르고 왜 무거운가

> 브라우저끼리 직접 미디어를 주고받기 위해 만든 기술 묶음.
> 전송은 RTP 그대로인데, 그 앞에 붙은 연결 수립 절차가 복잡하다.

## 왜 필요한가

브라우저에서 **1초 이하 지연**으로 영상을 보는 현실적인 방법이 이것뿐이다.
RTSP 는 브라우저가 못 받고, HLS 는 지연이 크다.

그리고 NAT 뒤에 있는 카메라에 **포트 개방 없이** 접속할 수 있다.
가정·소규모 설치에서 이 점이 결정적이다.

## 최소 이해 수준

- **미디어 전송은 RTP/SRTP 다.** 새로운 전송 방식이 아니다.
  → [RTP · RTCP](RTP.md)
- **복잡한 것은 연결 수립이다.** 다섯 조각을 알아야 한다.

  | 조각 | 역할 |
  |---|---|
  | **SDP** | 「내가 지원하는 코덱과 설정은 이렇다」는 명세 교환 |
  | **시그널링** | SDP 를 주고받는 통로. **규격에 없다** — 직접 만들어야 한다 |
  | **ICE** | 서로 닿을 수 있는 경로(후보)를 찾아 고르는 절차 |
  | **STUN** | 「나의 공인 IP·포트가 무엇인가」를 알려주는 서버 |
  | **TURN** | 직접 연결이 안 될 때 중계해 주는 서버 |

- **시그널링은 자유다.** WebSocket · HTTP · MQTT 무엇이든 된다.
  대신 **아무도 만들어 주지 않는다.** 이것이 「무거운」 이유의 절반이다.
  → [REST API · WebSocket](REST와WebSocket.md)
- **ICE 후보 세 종류.**
  - `host` — 내 로컬 IP. 같은 네트워크면 이걸로 붙는다
  - `srflx` — STUN 으로 알아낸 공인 주소. NAT 통과용
  - `relay` — TURN 중계 주소. 마지막 수단
- **TURN 이 필요한 비율이 무시할 수 없다.** 대칭 NAT 끼리는 직접 연결이 안 된다.
  TURN 은 모든 트래픽을 중계하므로 **서버 대역폭이 시청자 수에 비례**한다.
  「P2P 니까 서버가 필요 없다」가 성립하지 않는 지점이다.
- **암호화가 필수다.** SRTP 를 끌 수 없고, 키는 DTLS 로 협상한다.
  그래서 인증서가 필요하지만 **자체 서명이어도 된다** — 지문을 SDP 로 미리 교환하고
  그것과 대조하기 때문이다. → [TLS · X.509](../보안/TLS-X509.md)
- **코덱 제약.** H.264 는 대부분 되고, **H.265 는 사실상 안 된다.**
  카메라가 H.265 만 내보내면 트랜스코딩이 필요하고, 그러면 이득이 사라진다.
  → [H.265](../압축/H265.md)
- **`getUserMedia` 와 무관하다.** 카메라 기기가 보내는 쪽이면
  브라우저 API 가 아니라 서버 측 구현(`libwebrtc` · Pion · GStreamer `webrtcbin` 등)을 쓴다.

## 직접 해보기

### 1. STUN 으로 내 공인 주소 알아보기

```bash
# stunclient (stuntman 패키지)
stunclient stun.l.google.com 19302
```

`Mapped address` 가 공인 IP·포트다. 여러 번 실행해서 **포트가 매번 바뀌면**
대칭 NAT 일 가능성이 높고, 그러면 TURN 이 필요하다.

### 2. 브라우저에서 ICE 후보 보기

브라우저 콘솔에서:

```js
const pc = new RTCPeerConnection({iceServers:[{urls:'stun:stun.l.google.com:19302'}]});
pc.onicecandidate = e => e.candidate && console.log(e.candidate.candidate);
pc.createDataChannel('x');
pc.createOffer().then(o => pc.setLocalDescription(o));
```

`typ host` · `typ srflx` · `typ relay` 가 각각 몇 개 나오는지 본다.
`srflx` 가 없으면 STUN 서버에 못 닿은 것이다.

### 3. 실제로 어느 경로로 붙었는지 확인

크롬에서 `chrome://webrtc-internals` 를 열고 연결 중에 본다.
`selectedCandidatePair` 가 `relay` 면 TURN 을 타고 있다 —
**대역폭 비용이 발생하고 지연도 는다.**

### 4. 지연 재기

```
① 초 단위 시계를 카메라로 찍는다
② 브라우저 재생 화면과 실제 시계를 한 컷에 담아 사진을 찍는다
```

HLS 와 같은 방법이다. WebRTC 는 보통 0.2~0.5초가 나온다.
1초를 넘으면 어딘가 버퍼가 끼어 있다. → [HLS · DASH](HLS-DASH.md)

### 5. 통계로 품질 보기

```js
setInterval(async () => {
  const s = await pc.getStats();
  s.forEach(r => {
    if (r.type === 'inbound-rtp' && r.kind === 'video')
      console.log('유실', r.packetsLost, '지터', r.jitter, '프레임', r.framesPerSecond);
  });
}, 2000);
```

`packetsLost` 가 계속 늘면 회선이나 경로 문제다. → [RTP](RTP.md)

### 6. 가장 빠른 실습 경로

카메라에 직접 붙이기 전에, RTSP → WebRTC 변환 서버로 원리를 먼저 본다.

```bash
# MediaMTX 같은 서버가 RTSP 를 받아 WebRTC 로 내보낸다
# 설정에 RTSP 원본을 넣고 브라우저로 접속하면 동작을 확인할 수 있다
```

**직접 구현하기 전에 동작하는 것을 한 번 보는 편이 훨씬 빠르다.**

## 더 들어가면

- **DTLS-SRTP.** DTLS 핸드셰이크로 키를 만들고 그 키로 SRTP 를 돌린다.
  인증서 지문을 SDP 의 `a=fingerprint` 로 미리 교환하는 것이 핵심이다.
- **혼잡 제어 (GCC).** 수신 측 지연 변화를 보고 송신 비트레이트를 실시간으로 낮춘다.
  RTSP 에는 없는 기능이고, **회선이 나쁠 때 끊기지 않고 화질이 떨어지는** 이유다.
- **NACK · PLI · FIR.** 유실된 패킷 재전송 요청, 키프레임 재전송 요청.
  RTCP 확장으로 동작한다. 이것 때문에 유실 복구가 RTSP/UDP 보다 낫다.
- **SFU.** 시청자가 많을 때 중앙 서버가 스트림을 받아 여러 명에게 나눠 준다.
  디코딩하지 않고 전달만 하므로 트랜스코딩보다 싸다.
- **`whip` / `whep`.** 시그널링을 HTTP 한 번으로 표준화하려는 규격.
  「시그널링을 직접 만들어야 한다」는 문제를 줄여 준다.
- **데이터 채널.** 미디어 말고 임의 데이터도 보낼 수 있다.
  PTZ 제어 명령을 같은 연결로 보내는 데 쓸 수 있다.

## 흔한 오해

### 「WebRTC 는 P2P 라서 서버가 필요 없다」

최소 셋이 필요하다 — **시그널링 서버 · STUN 서버 · (자주) TURN 서버.**
그리고 TURN 을 타는 연결은 트래픽 전체가 서버를 지나간다.
비용 계산에서 이것을 빼면 나중에 크게 틀어진다.

### 「지연이 낮으니 감시에 무조건 유리하다」

연결 수립이 느리다. ICE 후보 수집과 DTLS 핸드셰이크에 수백 밀리초~수 초가 든다.
**32채널을 한 화면에 띄우면 전부 붙는 데 오래 걸리고** 연결 관리도 복잡하다.
채널 수가 많은 관제에는 RTSP 가 여전히 단순하다.

### 「브라우저 API 만 쓰면 된다」

보내는 쪽이 카메라라면 브라우저가 없다. 서버 측 WebRTC 스택을 붙여야 하고,
그 스택이 SoC 에서 도는지, 크로스 컴파일이 되는지가 실제 관문이다.
→ [크로스 컴파일](../BSP/크로스컴파일.md)

### 「암호화를 끄면 가벼워진다」

끌 수 없다. 규격이 SRTP 를 요구한다. 다만 SRTP 자체의 비용은 크지 않다 —
무거운 것은 암호화가 아니라 **연결 수립 절차와 혼잡 제어**다.

### 「NAT 뒤에서도 항상 붙는다」

대칭 NAT 끼리, 또는 UDP 를 전면 차단한 망에서는 직접 연결이 안 된다.
그때는 TURN 이 TCP·TLS 로 중계한다. **TURN 없이 배포하면
일부 고객 환경에서만 안 되는 문제**가 되고, 그 원인을 찾기 어렵다.
