# 멀티스레드 프로그래밍

> 메모리를 공유하는 여러 실행 흐름을 안전하게 다루는 일.
> 어려운 이유는 **버그가 재현되지 않기 때문**이다.

## 왜 필요한가

영상 파이프라인은 자연스럽게 여러 단계로 나뉜다 —
캡처 → 인코딩 → 전송. 각 단계를 스레드로 두면 서로 기다리지 않고 돌 수 있다.

문제는 그 사이의 버퍼를 공유한다는 것이다.
**한쪽이 쓰는 중에 다른 쪽이 읽으면** 깨진 프레임이 나오거나 프로그램이 죽는다.

## 최소 이해 수준

- **경쟁 조건(race).** 두 스레드가 같은 데이터를 동시에 만져 결과가 순서에 의존하는 상태.
  **대개 재현되지 않고, 부하가 높을 때만 나타난다.**
- **잠금의 기본형.**
  ```c
  pthread_mutex_lock(&m);
  /* 공유 데이터 조작 */
  pthread_mutex_unlock(&m);
  ```
  C++ 이라면 스코프로 관리한다 — 예외가 나도 풀린다.
  ```cpp
  { std::lock_guard<std::mutex> g(m); /* ... */ }
  ```
  → [Modern C++](../관제/ModernCpp.md)
- **조건 변수.** 「조건이 만족될 때까지 기다린다」를 구현한다.
  ```cpp
  std::unique_lock<std::mutex> lk(m);
  cv.wait(lk, []{ return !queue.empty(); });   // 술어(predicate)를 반드시 넣는다
  ```
  ⚠ **술어 없는 `wait` 를 쓰면 안 된다.** 가짜 깨어남(spurious wakeup)이 있고,
  신호가 먼저 와 있으면 영원히 기다린다.
- **원자적 연산.** 단순한 카운터라면 잠금 없이 된다.
  ```cpp
  std::atomic<int> frames{0};
  frames.fetch_add(1, std::memory_order_relaxed);
  ```
  **`volatile` 은 원자성을 주지 않는다.** 스레드 동기화 용도가 아니다.
- **교착(deadlock)의 조건.** 둘 이상이 서로가 가진 잠금을 기다린다.
  가장 흔한 원인은 **잠금 순서가 코드마다 다른 것**이다.
  ```
  스레드 A: lock(X) → lock(Y)
  스레드 B: lock(Y) → lock(X)      ← 순서가 반대. 교착 가능
  ```
  **규칙: 잠금에 전역 순서를 정하고 항상 그 순서로 잡는다.**
- **잠금 범위를 좁게.** 잠근 채로 I/O 하거나 인코딩하면 다른 스레드가 다 멈춘다.
  **데이터를 꺼내고 바로 풀고, 무거운 일은 밖에서** 한다.
  ```cpp
  Frame f;
  { std::lock_guard<std::mutex> g(m); f = std::move(queue.front()); queue.pop(); }
  encode(f);          // 잠금 밖에서
  ```
- **생산자-소비자 큐가 기본 패턴이다.** 영상 파이프라인의 표준 구조다.
  **큐 크기에 상한을 두는 것**이 중요하다 — 없으면 소비자가 느릴 때
  메모리가 무한히 는다.
- **오래된 프레임은 버린다.** 실시간 영상에서 밀린 프레임은 가치가 없다.
  큐가 차면 **가장 오래된 것을 버리는 정책**이 지연 누적을 막는다.
- **스레드 안전하지 않은 함수들.** `strtok` · `localtime` · `getenv` 등.
  `_r` 접미사 버전을 쓴다(`strtok_r` · `localtime_r`).

## 직접 해보기

### 1. 경쟁 조건을 눈으로 보기

```cpp
#include <thread>
#include <vector>
#include <cstdio>
long counter = 0;                    // 보호 없음
int main() {
    std::vector<std::thread> ts;
    for (int i = 0; i < 8; ++i)
        ts.emplace_back([]{ for (int j = 0; j < 200000; ++j) ++counter; });
    for (auto& t : ts) t.join();
    printf("%ld (기대 1600000)\n", counter);
}
```

```bash
g++ -std=c++17 -O2 -pthread race.cpp -o race
for i in 1 2 3 4 5; do ./race; done
```

**매번 다른 값이 나온다.** `-O0` 으로 빌드하면 덜 나타나는 것도 확인해 본다 —
그래서 「디버그 빌드에서는 괜찮은데 릴리스에서 죽는다」가 생긴다.

### 2. 도구로 잡기

```bash
g++ -std=c++17 -g -pthread -fsanitize=thread race.cpp -o race_t && ./race_t
```

`WARNING: ThreadSanitizer: data race` 가 정확한 줄 번호와 함께 나온다.
**이 도구 하나가 멀티스레드 디버깅의 절반이다.**

```bash
valgrind --tool=helgrind ./race 2>&1 | head -30
```

### 3. 생산자-소비자 큐 만들어 보기

```cpp
#include <mutex>
#include <condition_variable>
#include <deque>
#include <optional>

template <class T>
class BoundedQueue {
    std::mutex m_;
    std::condition_variable cv_;
    std::deque<T> q_;
    size_t cap_;
    bool closed_ = false;
public:
    explicit BoundedQueue(size_t cap) : cap_(cap) {}

    /* 가득 찼으면 가장 오래된 것을 버린다 — 실시간 영상에 맞는 정책 */
    void push(T v) {
        { std::lock_guard<std::mutex> g(m_);
          if (q_.size() >= cap_) q_.pop_front();
          q_.push_back(std::move(v)); }
        cv_.notify_one();
    }

    std::optional<T> pop() {
        std::unique_lock<std::mutex> lk(m_);
        cv_.wait(lk, [this]{ return !q_.empty() || closed_; });
        if (q_.empty()) return std::nullopt;           // 종료
        T v = std::move(q_.front()); q_.pop_front();
        return v;
    }

    void close() {
        { std::lock_guard<std::mutex> g(m_); closed_ = true; }
        cv_.notify_all();                              // 전부 깨운다
    }
};
```

⚠ **`close()` 가 없으면 종료할 수 없다.** 소비자 스레드가 `wait` 에서
영원히 잠들어 프로그램이 끝나지 않는다. 이것을 빠뜨린 코드가 아주 많다.

### 4. 교착을 재현하고 잡기

```cpp
std::mutex X, Y;
void a() { std::lock_guard<std::mutex> g1(X); std::this_thread::sleep_for(
             std::chrono::milliseconds(10)); std::lock_guard<std::mutex> g2(Y); }
void b() { std::lock_guard<std::mutex> g1(Y); std::this_thread::sleep_for(
             std::chrono::milliseconds(10)); std::lock_guard<std::mutex> g2(X); }
```

멈춘 뒤 어디서 멈췄는지 본다.

```bash
gdb -p <PID> -batch -ex 'thread apply all bt' 2>/dev/null | grep -A3 'Thread'
```

**두 스레드가 서로 다른 뮤텍스에서 기다리고 있으면 교착이다.**

해결: 순서를 통일하거나 한 번에 둘을 잡는다.

```cpp
std::scoped_lock g(X, Y);    // 교착 회피 알고리즘이 들어 있다
```

### 5. 잠금 경쟁이 있는지 재기

```bash
perf record -e 'syscalls:sys_enter_futex' -p <PID> -- sleep 5 2>/dev/null
perf report 2>/dev/null | head -20
```

`futex` 호출이 많으면 잠금에서 기다리는 시간이 길다는 뜻이다.
**잠금 범위를 좁히거나 데이터를 나눠야** 한다.

### 6. 스레드 이름 붙이기

```cpp
pthread_setname_np(pthread_self(), "capture");   // 15자 이내
```

```bash
ps -L -o tid,comm -p <PID>
top -H -p <PID>
```

**이름이 없으면 어느 스레드가 문제인지 알 수 없다.** 처음부터 붙이는 편이 낫다.

### 7. 종료 경로 시험

가장 자주 빠지는 시험이다.

```
① 프로그램을 정상 종료시킨다 (SIGTERM)
② 모든 스레드가 끝나는지 확인한다
③ 30초 안에 프로세스가 사라지는지 본다
```

```bash
kill -TERM <PID>; sleep 30; ps -p <PID> && echo "종료 실패"
```

**남아 있으면 어떤 스레드가 조건 변수나 블로킹 I/O 에서 멈춘 것**이다.

## 더 들어가면

- **읽기-쓰기 잠금.** 읽기가 압도적으로 많으면 `std::shared_mutex` 가 유리하다.
  다만 구현 비용이 커서 짧은 임계 구역에서는 일반 뮤텍스가 빠를 수 있다.
- **메모리 순서(memory order).** `relaxed` · `acquire` · `release` · `seq_cst`.
  성능을 위해 완화할 수 있지만 **틀리면 재현 불가능한 버그**가 된다.
  확신이 없으면 기본값(`seq_cst`)을 쓴다.
- **스레드 로컬 저장소.** `thread_local` 로 스레드마다 별도 변수를 둔다.
  잠금 없이 상태를 유지할 수 있다.
- **락 프리 큐.** 잠금 없이 원자적 연산만으로 만든 큐.
  빠르지만 검증이 어렵다. **직접 만들기보다 검증된 구현을 쓴다.**
- **우선순위 역전.** 낮은 우선순위 스레드가 잠금을 쥔 채 밀리면
  높은 우선순위 스레드가 못 나아간다.
  `PTHREAD_PRIO_INHERIT` 뮤텍스로 완화한다.
  → [프로세스 · 스레드 · 스케줄링](프로세스와스레드.md)
- **스레드 풀.** 작업마다 스레드를 만들지 않고 미리 만든 스레드가 일을 가져간다.
  채널 수가 변하는 관제 프로그램에서 유용하다.
- **긴 연결과 주기 확인.** 스트리밍 스레드가 세션 유효성을 주기적으로 확인해야 한다면,
  **확인이 세션을 갱신하지 않게** 읽기 전용 검사 함수를 따로 둔다.
  갱신하는 함수를 쓰면 연결이 열려 있는 동안 세션이 영원히 살아난다.
  → [인증과 인가](../보안/인증과인가.md)

## 흔한 오해

### 「`volatile` 을 붙이면 스레드 안전해진다」

`volatile` 은 컴파일러 최적화를 막을 뿐 원자성도 메모리 순서도 보장하지 않는다.
**하드웨어 레지스터 접근용**이고 스레드 동기화용이 아니다.
`std::atomic` 을 쓴다.

### 「테스트에서 통과했으니 경쟁 조건이 없다」

경쟁 조건은 타이밍에 의존한다. 개발 PC 에서 안 나타나던 것이
느린 보드나 코어 수가 다른 기기에서 나타난다.
**`-fsanitize=thread` 로 돌려 보는 것이 유일하게 믿을 만한 방법**이다.

### 「잠금을 크게 잡으면 안전하다」

안전하지만 병렬성이 사라진다. 극단적으로는 스레드를 쓰는 의미가 없어진다.
그리고 **잠금 범위가 크면 교착 가능성도 커진다.**

### 「큐에 상한을 두면 프레임을 잃는다」

상한이 없으면 메모리가 늘고, 지연도 쌓인다.
실시간 영상에서 3초 밀린 프레임은 이미 쓸모가 없으므로
**버리는 것이 옳은 선택**이다. 다만 몇 장 버렸는지는 세서 기록한다.

### 「스레드를 분리(detach)하면 관리가 편하다」

프로그램이 종료할 때 그 스레드가 무엇을 하고 있는지 알 수 없다.
객체가 파괴된 뒤에 접근하면 죽는다. **`join` 할 수 있게 만드는 편이 낫다.**

### 「조건 변수는 신호를 놓치지 않는다」

놓친다. `notify` 를 부르는 시점에 아무도 `wait` 하고 있지 않으면 그 신호는 사라진다.
그래서 **상태를 함께 두고 술어로 확인**해야 한다.
