# 커널 공간 vs 유저 공간

> 리눅스가 메모리와 권한을 둘로 나눠 놓은 것.
> 응용 프로그램은 유저 공간에 있고, 하드웨어에 닿으려면 경계를 넘어야 한다.

## 왜 필요한가

「이 문제가 커널 쪽인가 응용 쪽인가」가 디버깅의 첫 갈림길이다.
경계를 알면 어느 도구를 써야 하는지가 정해진다 —
유저 공간이면 `gdb`·`strace`, 커널이면 `dmesg`·`ftrace`.

그리고 성능 문제의 상당수가 **경계를 너무 자주 넘는 것**이다.
프레임마다 커널을 몇 번 왕복하는지가 처리량을 결정한다.

## 최소 이해 수준

- **권한 수준이 하드웨어로 분리돼 있다.** CPU 에 특권 모드가 있고,
  유저 공간 코드는 하드웨어 레지스터에 직접 접근할 수 없다.
  **잘못된 응용이 시스템 전체를 죽이지 못하게** 하는 장치다.
- **넘는 방법은 시스템 콜뿐이다.** `read` · `write` · `ioctl` · `mmap` 등.
  라이브러리 함수는 결국 시스템 콜을 부른다.
  ```
  응용 코드 → libc (fread) → 시스템 콜 (read) → 커널 → 드라이버 → 하드웨어
  ```
- **경계를 넘는 비용이 있다.** 문맥 전환과 인자 검사가 들어간다.
  한 번은 수백 나노초 수준이지만, **프레임당 수천 번이면 무시할 수 없다.**
- **메모리가 분리돼 있다.** 커널은 유저 메모리를 직접 못 읽고
  `copy_from_user` / `copy_to_user` 로 옮긴다.
  이것이 **`mmap` 이 빠른 이유**다 — 복사를 없애고 같은 물리 메모리를 양쪽이 본다.
- **실패가 다르게 나타난다.**

  | | 유저 공간 | 커널 공간 |
  |---|---|---|
  | 잘못된 포인터 | `SIGSEGV` — 그 프로세스만 죽는다 | Oops / 패닉 — 시스템이 흔들린다 |
  | 무한 루프 | 스케줄러가 다른 일을 계속 한다 | 시스템이 멈출 수 있다 |
  | 메모리 누수 | 프로세스 종료 시 회수된다 | **재부팅까지 남는다** |
  | 디버깅 | `gdb` 로 붙는다 | `printk` · `ftrace` · `kgdb` |

- **ABI 는 안정적이고 커널 내부 API 는 아니다.**
  시스템 콜 인터페이스는 깨지지 않는다는 규칙이 있어 옛 바이너리가 새 커널에서 돈다.
  반면 드라이버가 쓰는 내부 함수는 언제든 바뀐다.
  → [커널 구조 · 모듈](../BSP/커널구조.md)
- **커널 상태를 보는 창구가 셋이다.**
  ```
  /proc    프로세스와 커널 정보
  /sys     장치 계층 구조와 속성
  debugfs  디버깅 전용 (/sys/kernel/debug)
  ```
- **무엇을 커널에 넣을지의 기준.** 타이밍이 정확해야 하거나 하드웨어에 직접 닿는 것만.
  **나머지는 유저 공간이 훨씬 안전하고 개발이 빠르다.**

## 직접 해보기

### 1. 경계를 넘는 순간을 눈으로 보기

```bash
strace -c ls /tmp
```

시스템 콜별 호출 횟수와 시간이 나온다.
**응용이 커널에 무엇을 부탁했는지의 전체 목록**이다.

```bash
strace -f -e trace=openat,read,ioctl <프로그램> 2>&1 | head -40
```

### 2. 영상 캡처가 커널을 몇 번 왕복하는지

```bash
strace -c -e trace=ioctl v4l2-ctl -d /dev/video0 \
  --stream-mmap --stream-count=30 2>&1 | tail -10
```

프레임 30장에 `ioctl` 이 몇 번인지 센다.
`VIDIOC_QBUF`/`DQBUF` 가 프레임당 각 한 번이면 최소 경로다.
→ [V4L2](../영상/V4L2.md)

### 3. 복사가 있는 경로와 없는 경로 비교

```bash
# read() 기반 — 커널→유저 복사가 프레임마다 일어난다
time v4l2-ctl -d /dev/video0 --stream-user --stream-count=100 >/dev/null

# mmap 기반 — 복사가 없다
time v4l2-ctl -d /dev/video0 --stream-mmap --stream-count=100 >/dev/null
```

고해상도에서 차이가 분명히 난다. → [파일 디스크립터 · ioctl · mmap](fd-ioctl-mmap.md)

### 4. 시간이 어디에 쓰이는지 가르기

```bash
/usr/bin/time -v <프로그램> 2>&1 | grep -E 'wall clock|User time|System time'
```

```
User time    유저 공간에서 쓴 CPU
System time  커널 안에서 쓴 CPU
```

`System time` 이 크면 **시스템 콜이 많거나 I/O 가 많은 것**이다.
그때는 응용 알고리즘을 최적화해도 효과가 없다.

### 5. 커널 쪽 정보 읽어 보기

```bash
cat /proc/meminfo | head
cat /proc/interrupts | head
cat /proc/<PID>/status | grep -E 'Threads|VmRSS|voluntary'
ls /sys/class/video4linux/
```

`voluntary_ctxt_switches` 와 `nonvoluntary_ctxt_switches` 를 비교하면
**스스로 기다린 것**과 **강제로 빼앗긴 것**이 구분된다.

### 6. 커널 오류와 응용 오류를 구분

```bash
# 응용이 죽었다
dmesg | grep -i segfault
coredumpctl list 2>/dev/null | tail

# 커널이 문제다
dmesg -l err,crit,alert,emerg
dmesg | grep -iE 'oops|BUG:|call trace'
```

`Call Trace` 가 보이면 커널 안에서 터진 것이므로
**응용을 고쳐서 해결되지 않는다.**

### 7. 커널 함수 호출을 추적해 보기

```bash
sudo mount -t debugfs none /sys/kernel/debug 2>/dev/null
cd /sys/kernel/debug/tracing
echo function > current_tracer
echo 'vb2_*' > set_ftrace_filter      # V4L2 버퍼 관련만
echo 1 > tracing_on
# 잠시 후
echo 0 > tracing_on
head -40 trace
```

`printk` 를 넣지 않고도 **어느 함수가 불렸는지** 볼 수 있다.

## 더 들어가면

- **`vDSO`.** `gettimeofday` 같은 일부 호출은 커널로 진입하지 않고
  공유 페이지에서 답한다. 그래서 시간 조회가 매우 싸다.
- **`io_uring`.** 시스템 콜 횟수를 줄이는 최신 방식.
  요청을 링 버퍼에 쌓아 한 번에 처리한다. 고성능 I/O 에서 쓴다.
  → [비동기 I/O](비동기IO.md)
- **유저 공간 드라이버.** UIO · VFIO 로 하드웨어를 유저 공간에서 직접 다룬다.
  개발이 쉽고 안전하지만 인터럽트 지연이 커진다.
  벤더가 독자 드라이버를 이렇게 만드는 경우가 있다(GPL 회피 목적도 있다).
- **`copy_from_user` 의 검사.** 커널은 유저가 준 포인터를 절대 믿지 않는다.
  주소 범위와 접근 권한을 확인한다. **이 검사를 빠뜨리는 것이 전형적인 커널 취약점**이다.
- **seccomp.** 프로세스가 쓸 수 있는 시스템 콜을 제한한다.
  경계를 좁혀 공격 표면을 줄이는 실제 조치다.
- **컨테이너와 네임스페이스.** 같은 커널을 공유하면서 유저 공간만 분리한다.
  가상머신과 다른 점이 이것이다.

## 흔한 오해

### 「커널에서 하면 빠르다」

경계를 넘는 비용은 줄지만, 커널 코드는 디버깅이 어렵고 실수의 대가가 크다.
그리고 대부분의 성능 문제는 **경계를 넘는 횟수**가 원인이지
넘는 비용 자체가 아니다. **`mmap` 이나 일괄 처리로 횟수를 줄이는 것**이 먼저다.

### 「`ioctl` 이 성공했으니 하드웨어가 동작했다」

`ioctl` 은 드라이버까지 갔다는 뜻이다. 드라이버가 I2C 로 보낸 값이
칩에 도착했는지는 별개다. **경계마다 확인 지점을 두어야** 범위가 좁혀진다.
→ [오실로스코프](../하드웨어/계측.md)

### 「응용이 죽었으니 응용 버그다」

드라이버가 잘못된 값을 돌려줘서 응용이 죽는 경우가 있다.
`dmesg` 를 같이 보지 않으면 원인을 잘못 짚는다.

### 「커널 로그가 없으면 커널은 정상이다」

`printk` 가 없는 경로는 조용히 실패한다. 그리고 로그 레벨 때문에
출력되지 않는 메시지가 있다.

```bash
cat /proc/sys/kernel/printk      # 현재 레벨
dmesg -n 8                       # 전부 보이게
```

### 「유저 공간이니 메모리를 마음대로 써도 된다」

프로세스가 죽으면 회수되지만, 임베디드에서는 그 전에 시스템이 OOM 을 겪는다.
카메라 한 대가 메모리를 먹으면 **다른 프로세스가 죽는다.**

```bash
dmesg | grep -i 'killed process'
```
