# 프로세스 · 스레드 · 스케줄링

> 프로세스는 격리된 실행 단위, 스레드는 메모리를 공유하는 실행 흐름.
> 스케줄러가 그중 누가 CPU 를 쓸지 정한다.

## 왜 필요한가

카메라 펌웨어는 여러 일을 동시에 한다 — 캡처 · 인코딩 · 전송 · 웹 서버 ·
감시 데몬. 이것을 프로세스로 나눌지 스레드로 나눌지가 **구조의 첫 결정**이다.

그리고 프레임이 떨어지는 문제의 상당수가 스케줄링이다.
「CPU 는 여유가 있는데 프레임이 밀린다」면 우선순위나 지연을 봐야 한다.

## 최소 이해 수준

- **프로세스와 스레드의 차이.**

  | | 프로세스 | 스레드 |
  |---|---|---|
  | 메모리 | 각자 독립 | **공유** |
  | 통신 | 파이프·소켓·공유메모리 | 변수로 직접 |
  | 격리 | 하나가 죽어도 남는다 | 하나가 죽으면 전부 죽는다 |
  | 생성 비용 | 크다 | 작다 |
  | 디버깅 | 쉽다 | 어렵다 (경쟁 조건) |

  **리눅스 커널은 둘을 같은 것(task)으로 다룬다.** 무엇을 공유하는지만 다르다.
- **나누는 기준.** 실패가 번지면 안 되는 것은 **프로세스**로 분리한다.
  카메라 채널 하나가 죽어서 전체 관제가 멈추면 안 된다면 프로세스다.
  같은 프레임 버퍼를 계속 주고받아야 하면 스레드다.
- **스케줄링 정책 세 가지.**

  | 정책 | 성격 | 우선순위 |
  |---|---|---|
  | `SCHED_OTHER` (CFS) | 기본. 공평하게 나눈다 | nice −20~19 |
  | `SCHED_FIFO` | 실시간. 양보하지 않는다 | 1~99 |
  | `SCHED_RR` | 실시간. 같은 우선순위끼리 돌려쓴다 | 1~99 |

  **실시간 정책은 더 높은 우선순위가 없으면 CPU 를 놓지 않는다.**
  무한 루프를 실시간으로 돌리면 시스템이 멈춘다.
- **`nice` 와 우선순위.** 값이 낮을수록 우선이다. 일반 프로세스는
  `nice` 로 조절하고, **지연이 중요한 스레드만 실시간 정책**으로 올린다.
- **CPU 친화도(affinity).** 특정 코어에 묶는다.
  캐시 지역성이 좋아지고, 인터럽트 처리 코어와 분리할 수 있다.
- **문맥 전환에는 비용이 있다.** 자발적(기다림)과 비자발적(빼앗김)을 구분해서 본다.
  비자발적 전환이 많으면 **CPU 경쟁**이 있는 것이다.
- **좀비와 고아.** 자식이 끝났는데 부모가 `wait` 하지 않으면 좀비로 남는다.
  프로세스 테이블을 차지하므로 **반드시 거둬야** 한다.
- **fork 후 exec.** `fork` 로 복제하고 `exec` 로 다른 프로그램이 된다.
  ⚠ **스레드가 있는 프로세스에서 `fork` 는 위험하다** —
  자식에는 호출한 스레드만 남고, 다른 스레드가 잡고 있던 잠금이 영원히 잠긴 채 복사된다.

## 직접 해보기

### 1. 프로세스와 스레드 확인

```bash
ps -eLf | head                       # L = 스레드까지
ps -eo pid,nlwp,rtprio,ni,pri,comm --sort=-nlwp | head
```

`nlwp` 가 스레드 수, `rtprio` 가 실시간 우선순위다.

```bash
cat /proc/<PID>/status | grep -E 'Threads|State|Cpus_allowed_list'
ls /proc/<PID>/task/                 # 스레드마다 디렉터리
```

### 2. 어느 스레드가 CPU 를 먹는지

```bash
top -H -p <PID>
```

`-H` 가 스레드 단위 표시다. **프로세스 단위로 보면 어느 일이 무거운지 알 수 없다.**

```bash
ps -L -o tid,pcpu,comm -p <PID> --sort=-pcpu | head
```

스레드에 이름을 붙여 두면 여기서 바로 보인다.

```c
pthread_setname_np(pthread_self(), "encoder");   /* 15자 제한 */
```

### 3. 문맥 전환 세기

```bash
grep -E 'voluntary|nonvoluntary' /proc/<PID>/status
```

```
voluntary_ctxt_switches      스스로 기다린 횟수 (정상적인 I/O 대기)
nonvoluntary_ctxt_switches   빼앗긴 횟수  ← 크면 CPU 경쟁
```

### 4. 우선순위를 올려 보기

```bash
# 실시간 정책으로 실행
sudo chrt -f 50 ./myapp

# 도는 스레드의 정책 바꾸기
sudo chrt -f -p 50 <TID>
chrt -p <TID>                        # 현재 정책 확인
```

⚠ **실시간으로 올린 코드에 무한 루프가 있으면 그 코어가 잠긴다.**
시험 전에 다른 터미널을 열어 두고, 가능하면 코어를 지정한다.

```bash
sudo taskset -c 2 chrt -f 50 ./myapp
```

### 5. 코어에 묶어 보기

```bash
taskset -c 0,1 ./myapp
taskset -pc <PID>                    # 현재 설정
sudo taskset -pc 3 <TID>             # 스레드 하나만 옮기기
```

**인터럽트가 몰리는 코어를 피하면** 프레임 지연이 줄어드는 경우가 있다.

```bash
cat /proc/interrupts | head
```

### 6. 지연을 실제로 재기

```bash
# 실시간 지연 측정 (rt-tests 패키지)
sudo cyclictest -t1 -p 80 -i 1000 -l 10000 -q
```

`Max` 값이 최악 지연이다. **평균이 아니라 최악값이 프레임 누락을 만든다.**

### 7. 어디서 멈춰 있는지 보기

```bash
cat /proc/<PID>/task/<TID>/stack 2>/dev/null    # 커널 스택 (권한 필요)
cat /proc/<PID>/wchan; echo                     # 무엇을 기다리는지
sudo gdb -p <PID> -batch -ex 'thread apply all bt' 2>/dev/null | head -40
```

멈춘 프로그램의 원인을 찾는 가장 빠른 방법이다.
→ [디버깅](../공통/디버깅.md)

### 8. 좀비 확인

```bash
ps -eo pid,ppid,stat,comm | awk '$3 ~ /^Z/'
```

나오면 부모가 `wait` 를 안 하는 것이다.

## 더 들어가면

- **CFS 의 동작.** 「가상 실행 시간」이 가장 적은 쪽에 CPU 를 준다.
  `nice` 는 그 시간이 흐르는 속도를 바꾼다. **완전한 비율 보장은 아니다.**
- **`PREEMPT_RT`.** 커널 안에서도 선점이 가능해져 최악 지연이 크게 줄어든다.
  전체 처리량은 조금 떨어진다. → [커널 구조](../BSP/커널구조.md)
- **인터럽트 스레드화.** 인터럽트 핸들러를 스레드로 만들어 우선순위를 줄 수 있다.
  영상 캡처 인터럽트를 다른 일보다 앞세우는 데 쓴다.
- **cgroup.** CPU · 메모리 · I/O 를 그룹 단위로 제한한다.
  채널 하나가 자원을 독점하지 못하게 막는 실제 수단이다.
  ```bash
  systemd-run --scope -p CPUQuota=50% ./myapp
  ```
- **`prctl` 과 워치독.** 프로세스가 살아 있는지 서로 감시하는 구조.
  부모가 죽으면 자식도 종료되게 하려면 `PR_SET_PDEATHSIG`.
- **단일 인스턴스 보장.** 같은 데몬이 두 개 돌면 자원을 다투거나
  기록을 서로 망친다. `flock` 으로 잠금 파일을 잡아 막는다.

  실측: 배포 절차에서 감시 스크립트가 데몬을 되살리는 동안 손으로 또 띄워
  **기록자가 둘이 되면서 감사 기록의 순번이 중복**된 일이 있었다.
  프로세스를 죽이고 다시 띄우는 절차에서 특히 조심해야 한다.
  → [감사기록](../보안/감사기록.md)

## 흔한 오해

### 「스레드를 많이 만들면 빠르다」

코어 수를 넘으면 문맥 전환만 늘어난다. 그리고 스레드마다 스택(기본 8MB 예약)이
필요해 **메모리가 적은 임베디드에서는 스레드 수 자체가 제약**이다.

```bash
ulimit -s                            # 스택 크기
```

### 「실시간 우선순위를 주면 프레임이 안 떨어진다」

우선순위는 **CPU 를 먼저 받는 것**이고, I/O 대기나 잠금 대기는 해결하지 않는다.
높은 우선순위 스레드가 낮은 우선순위 스레드의 잠금을 기다리면
오히려 더 나빠진다(우선순위 역전).

### 「CPU 사용률이 낮으니 여유가 있다」

지연이 문제일 수 있다. 30fps 는 33ms 주기이고, 한 번이라도 40ms 밀리면
프레임이 떨어진다. **평균 사용률이 아니라 최악 지연**을 봐야 한다.

### 「프로세스로 나누면 성능이 떨어진다」

프레임 버퍼를 복사해 넘기면 그렇다. 하지만 **공유 메모리나 DMABUF fd 를
소켓으로 넘기면** 복사가 없다. 격리의 이점을 성능 없이 얻을 수 있다.
→ [파일 디스크립터 · ioctl · mmap](fd-ioctl-mmap.md)

### 「스레드가 죽으면 그 스레드만 사라진다」

`SIGSEGV` 같은 치명적 시그널은 **프로세스 전체를 죽인다.**
한 채널의 디코더 버그가 32채널을 다 내리는 구조가 이래서 생긴다.

### 「멀티스레드가 있는데 `fork` 를 쓰면 편하다」

자식은 잠금 상태를 그대로 물려받으면서 그 잠금을 풀 스레드가 없다.
`fork` 직후 바로 `exec` 하는 경우만 안전하다.
그 목적이면 `posix_spawn` 을 쓰는 편이 낫다.
