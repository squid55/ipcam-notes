# 함정 모음

IP카메라 펌웨어를 만들면서 **실제로 막혔던 지점**을 모은 것이다. 문서에 적혀 있지 않거나,
적혀 있어도 읽고서는 알기 어려운 것들만 골랐다. 각 항목은 결론을 먼저 쓰고 근거를 뒤에 붙인다.

---

## 영상 · V4L2

### `-f H264` 는 동작하지 않는다

`v4l2rtspserver` 등에서 포맷 지정 옵션이 `getopt` 의 **선택적 인자**(`f::`)로 선언된 경우,
`-f H264` 는 옵션 값이 비어 있는 것으로 처리되고 `H264` 는 **장치명 목록**으로 넘어간다.
`-fH264` 처럼 붙여 써야 한다.

증상이 엉뚱하게 나타난다. 포맷 목록이 비어 초기화가 실패하는데 그 함수는 로그를 남기지
않고 `-1` 만 반환하므로, 보이는 것은 상위 계층의 `Cannot init device` 뿐이다. 동시에 장치가
두 개로 인식되어 스트림 경로에 접두어가 붙는다.

**시험할 때 성공한 것처럼 보일 수 있다.** 직전에 다른 도구가 `S_FMT` 로 포맷을 설정해 두었다면
`G_FMT` 가 그 값을 돌려주기 때문이다. 재부팅 직후에는 기본 포맷이 `0x0` 이라 반드시 실패한다.

### 프레임 크기가 일정하면 압축되지 않은 것이다

드라이버가 `MJPG` 요청을 받아들이고 `MJPG` 라고 보고하면서도 실제로는 비압축 프레임을 주는
경우가 있다. 압축 스트림은 프레임마다 크기가 달라지므로, **크기가 매번 동일하면** 압축이
일어나지 않은 것으로 봐야 한다.

예: 1280×720 에서 매 프레임 1,382,400 바이트가 오면 그것은 NV12 의 크기다.

### 인코더가 벤더 API 없이 표준 V4L2 로 노출되기도 한다

"하드웨어 인코더를 쓰려면 벤더 SDK 를 호출해야 한다"가 항상 참은 아니다. 일부 SoC 는
인코더를 별도 `/dev/videoN` 으로 올려두고, `S_FMT` 로 `H264` 를 지정하면 압축 스트림을 낸다.

확인 비용이 낮으므로 벤더 API 로 가기 전에 먼저 시도해 볼 값이 있다. 이 경로가 되면 표준
V4L2 도구를 그대로 쓸 수 있어 작업량이 크게 줄어든다.

### MJPEG 화질이 낮은 원인이 JPEG 품질이 아닐 수 있다

JPEG 품질 계수를 노출하지 않고 **비트레이트로만 제어**하는 인코더가 있다. 이 경우 화질
설정을 아무리 올려도 비트레이트가 낮으면 모자이크가 남는다.

또 하나 — H.264 용 레이트 컨트롤이 MJPEG 채널에도 걸려 있으면, 기본값(예: 3 Mbps)이
프레임당 수십 KB 로 나뉘어 품질이 무너진다. 하한을 두지 않으면 레이트 컨트롤이 진동한다.

### 정지 명령이 수 초 블로킹되면 순서를 바꾼다

`STREAMOFF` 가 수 초간 멈추고 오류를 내는 경우, ISP 가 프레임을 채우는 중에 정지 명령이
겹친 것이다. **버퍼 재큐를 먼저 중단하고, 진행 중인 프레임을 배출한 뒤, 그다음 `STREAMOFF`**
순서로 바꾸면 해소된다. 짧은 유예(수백 밀리초)만으로 충분한 경우가 많다.

스트리밍 서버에서는 이 순서를 지키지 않으면 클라이언트가 끊길 때마다 그만큼 블로킹된다.

### SPS/PPS 가 선두에 없다고 없는 것이 아니다

취득한 H.264 스트림의 첫 NAL 이 non-IDR 이라 파라미터셋이 빠진 것처럼 보일 수 있다.
NAL 을 전수 세어 보면 대개 일정 간격(예: 32프레임)마다 `SPS → PPS → IDR` 이 반복 삽입된다.
별도 제어가 필요 없다.

### 프레임 수만으로 센서 생존을 판정하면 안 된다

센서가 죽어도 ISP 는 검은 프레임을 규칙적으로 낸다. 프레임 카운트만 보는 진단 도구는
"정상"으로 보고한다.

**휘도 평면의 표준편차**를 함께 보면 즉시 갈린다. 완전히 균일한 화면은 표준편차가 0 에 가깝다.

관련: [압축되지 않은 프레임](#프레임-크기가-일정하면-압축되지-않은-것이다)

## 스트리밍

### live555 는 자기 클라이언트가 보내는 전송 헤더를 파싱하지 못한다

live555 서버의 `parseTransportHeader()` 는 `RTP/AVP`, `RTP/AVP/TCP`, `RTP/AVP/SAVP` 만
인식한다. 그런데 같은 라이브러리로 만든 클라이언트는 RFC 3711 표준 이름인
**`RTP/SAVP/TCP`** 를 보낸다. 결과는 `461 Unsupported Transport` 다.

VLC 도 내부적으로 live555 를 쓰므로 동일하게 실패한다. ffmpeg 은 SETUP 은 통과하지만
복호에 실패해 깨진 영상이 나온다 — **증상만 보면 서버 문제인지 클라이언트 문제인지 구분되지
않는다.** SETUP 의 Transport 헤더를 직접 봐야 원인이 갈린다.

### RTSP 서버의 인터페이스 지정 옵션이 HTTP 터널까지 묶을 수 있다

live555 기반 서버에서 수신 인터페이스를 지정하면 그 값이 라이브러리 전역
`ReceivingInterfaceAddr` 에 들어가고, HTTP 터널링 설정도 **같은 주소로 바인딩**된다.

"RTSP 는 외부, HTTP 는 루프백"처럼 나누려는 구성이 구조적으로 불가능해진다. 별도 포트를
열지 않으려는 설계에서는 이 제약이 결정적일 수 있다.

## 임베디드 리눅스

### 하드웨어 워치독이 유저스페이스 사망을 잡아주지 않는다

`CONFIG_WATCHDOG_MONITOR_THREAD=y` 로 빌드된 커널은 **커널 스레드가 워치독을 자동으로
먹인다.** 커널이 살아 있는 한 유저스페이스 프로세스가 전부 죽어도 리셋되지 않는다.

무인 운용 기기에서 "전원은 들어와 있는데 서비스가 없는" 상태가 무기한 지속될 수 있다.
생존 확인은 별도 감시 프로세스가 직접 해야 한다. 프로세스 존재만 보지 말고 **포트가 실제로
열려 있는지**도 함께 봐야 교착 상태를 잡는다.

### busybox 에서 `pidof <스크립트>.sh` 는 잡히지 않는다

셸 스크립트는 프로세스 목록에 인터프리터(`sh`)로 나타난다. 스크립트 이름으로는 매칭되지
않는다. 잠금이나 중복 실행 방지에 `pidof` 를 쓰면 항상 실패한다.

디렉터리 생성(`mkdir`)의 원자성을 이용한 잠금이 대안이다.

### `grep -c` 는 일치가 없을 때 0 을 출력하면서 종료코드 1 을 낸다

```sh
n=$(grep -c pattern file || echo 0)
```

일치가 없으면 `grep` 이 `0` 을 출력하고 **동시에** 종료코드 1 을 반환하므로 `|| echo 0` 이
실행된다. 결과는 `0\n0` 이다. 이 값으로 숫자 비교를 하면 실패한다.

값을 받은 뒤 형식을 검사하는 편이 안전하다.

### UBIFS 의 `df` 는 GC 전까지 부풀어 보인다

로그 구조 파일시스템이라 파일을 덮어쓰면 옛 내용이 회수될 때까지 자리를 함께 차지한다.
수 MB 짜리 파일을 연속으로 교체하면 사용률이 95% 까지 치솟았다가 잠시 뒤 돌아온다.

`du` 와 `df` 가 다른 것도 정상이다 — `du` 는 원본 크기, `df` 는 압축 후 매체 사용량이다.
같은 트리에서 `du` 12 MB / `df` 7 MB 처럼 벌어질 수 있다.

### initramfs 안의 스크립트는 루트 파일시스템 갱신으로 고칠 수 없다

네트워크 설정처럼 초기화 스크립트가 커널 이미지 안(initramfs)에 들어 있으면, 응용 파티션을
갱신해도 반영되지 않는다. 커널을 다시 굽거나, **그 스크립트가 끝난 뒤 값을 덮어쓰는** 방식을
쓸 수밖에 없다.

덮어쓰기 방식을 택할 때는 실패 안전하게 만들어야 한다. 설정 파일이 없거나 형식이 깨졌으면
아무것도 하지 않는 편이, 잘못된 값을 적용해 접속 불가를 만드는 것보다 낫다.

### 실행 중인 실행파일은 덮어쓸 수 없지만 이름 바꾸기는 된다

실행 중인 바이너리를 열어 쓰려 하면 `ETXTBSY` 가 난다. `tar` 로 그 자리에 풀면 실패한다.

같은 파일시스템 안에서라면 **`rename` 은 성공한다.** 실행 중인 프로세스는 옛 아이노드를
계속 쓰고, 새 파일이 그 이름을 차지한다. 서비스를 멈추지 않고 교체할 수 있다.

⚠ 다른 파일시스템으로 옮기면 `mv` 가 복사+삭제가 되므로 다시 `ETXTBSY` 다. 임시 디렉터리를
같은 파일시스템 안에 두어야 한다.

## 부트로더

### `bootdelay=0` 으로는 자동부팅 중단을 막지 못한다

U-Boot 의 `abortboot()` 는 `bootdelay >= 0` 이면 중단 여부를 확인한다. 그리고 확인 함수는
대기 루프에 들어가기 **전에** 이미 입력된 키가 있는지 한 번 본다.

```c
if (tstc()) { getchar(); abort = 1; }
```

따라서 대기 시간이 0 이어도 기동 시점에 키를 누르고 있으면 프롬프트로 들어간다.
실제로 막으려면 **`-2`** 여야 한다 — 이 값은 중단 확인 절차 자체를 건너뛴다.
`-1` 은 반대로 자동부팅을 하지 않고 프롬프트에 머무는 값이니 혼동하면 안 된다.

### `bootdelay` 는 세 곳에서 정해지고 뒤가 앞을 덮는다

```
컴파일 기본값  →  저장매체의 환경변수  →  장치 트리
```

컴파일 값만 고정하면 환경변수로 되돌릴 수 있다. U-Boot 소스 주석 자체가 그 이유를 밝힌다 —
장치 트리는 서명할 수 있지만 환경변수는 대개 저장매체에서 읽히기 때문이다.
고정이 필요하면 **서명된 장치 트리**에 넣는다.

## 웹 · CGI

### CGI 에서 `read` 로 POST 본문을 읽으면 멈춘다

웹서버는 stdin 을 닫지 않고 `CONTENT_LENGTH` 로 길이만 알려준다. 본문에 줄바꿈이 없으면
`read` 는 영원히 기다린다. 화면에는 아무것도 나오지 않는다.

```sh
BODY=$(head -c "$CONTENT_LENGTH")
```

⚠ **로컬 시험에서 `echo` 로 본문을 흘려보내면 재현되지 않는다.** `echo` 가 줄바꿈을 붙이기
때문이다. `printf` 와 타임아웃으로 시험해야 한다.

### `lighttpd -t` 는 인증서를 검증하지 않는다

설정 문법만 본다. 개인키와 인증서가 짝이 맞지 않아도, 인증서 자리에 아무 텍스트 파일을 넣어도
`Syntax OK` 가 나온다.

인증서 교체 절차에서 이것만 믿으면 **웹 서비스가 뜨지 않는 설정을 적용**하게 된다.
확인하려면 임시 포트로 실제 기동해 보는 수밖에 없다.

### 정적 파일에 캐시 지시가 없으면 브라우저가 며칠간 옛 파일을 쓴다

`Cache-Control` 이 없으면 브라우저는 추측 캐싱을 한다 — `(현재 − Last-Modified)` 의 10%
정도를 신선한 것으로 간주하고 **서버에 묻지 않는다.** 파일이 2주 안 바뀌었으면 그 창이
1~2일이 된다.

펌웨어를 갱신해도 화면 코드가 옛 동작을 계속하는 상태가 만들어진다. 서버는 고쳐졌는데
증상이 그대로라 원인을 서버에서 찾게 된다.

`max-age=0` 은 캐시를 끄는 것이 아니라 매번 확인시키는 것이다. 내용이 그대로면 304 한 줄만
오간다.

### CSP `img-src 'self'` 는 `data:` URI 를 막는다

스트림을 끊으려고 1×1 투명 GIF 를 `data:` URI 로 넣는 관용구가 있는데, CSP 가 걸려 있으면
차단된다. 위반이 매번 쌓이고 동작이 브라우저 구현에 의존하게 된다.

`removeAttribute('src')` 가 CSP 와 무관하게 진행 중인 로드를 취소하며, `src` 속성이 없는
`<img>` 는 깨진 이미지 아이콘도 그리지 않는다.

### 스트림이 정상 종료되면 `onerror` 가 뜨지 않는다

`multipart/x-mixed-replace` 로 보내던 연결을 서버가 정상적으로 닫으면 오류가 아니므로
`img.onerror` 가 발생하지 않는다. `<img>` 는 마지막 프레임을 그대로 들고 있는다.

결과는 **생방송처럼 보이는 정지화면**이다. 고장 중 가장 나쁜 종류다.
프레임 도착 간격을 감시하는 타이머를 따로 둬야 한다.

## 교차 빌드

### 정적 링크에서 `getaddrinfo` 경고의 의미

```
warning: Using 'getaddrinfo' in statically linked applications requires
at runtime the shared libraries from the glibc version used for linking
```

이름 해석(NSS)이 런타임에 공유 라이브러리를 dlopen 하기 때문에 나온다. 정적 링크의 목적이
"대상 보드에 라이브러리를 두지 않는 것"이라면 이 경로만 예외가 된다.

IP 주소로만 접속하는 구성이면 실무상 문제가 없지만, 호스트명을 쓰는 순간 드러난다.

### 바이너리에 빌드 경로가 박히는 두 경로

배포물에 개발자 홈 디렉터리가 남는 일이 흔하다. 원인이 둘이고 대책이 다르다.

**① 라이브러리의 설정 경로 상수** — OpenSSL 의 `openssldir` 처럼 빌드 시 고정되는 값.
중립적인 경로로 다시 빌드해야 한다.

**② `__FILE__` 매크로** — 소스 절대경로가 박힌다. `-ffile-prefix-map` 으로 치환한다.

⚠ ②의 함정 — 일부 라이브러리는 **컴파일 명령줄 문자열 자체**를 바이너리에 넣는다.
그러면 `-ffile-prefix-map=/home/사용자=/build` 라는 인자의 절대경로가 그대로 남는다.
빌드 디렉터리 안에서 상대경로(`-ffile-prefix-map=.=이름`)로 지정해야 0 건이 된다.

## 진단 태도

### 한 번에 변수 하나만 바꾼다

원인을 좁힐 때 두 가지를 동시에 바꾸면 무엇이 효과가 있었는지 알 수 없다. 이 프로젝트에서
ISP 블로킹 원인을 두 번 오진했는데, 두 번 다 정상 동작하는 상태에서 파라미터와 출력 대상을
함께 바꾼 것이 원인이었다.

### 성공한 것처럼 보이는 실패를 의심한다

이 문서의 절반이 그런 종류다.

- 컴파일은 성공하고 **내용만 틀린** 빌드 ([검색 경로](#));
- `Syntax OK` 를 내는 **깨진 인증서 설정**;
- 프레임은 오는데 **센서는 죽은** 상태;
- 서버는 고쳤는데 **브라우저가 옛 코드를 쓰는** 상태.

돌려보고 결과를 눈으로 확인하는 것 외에 방법이 없다.
