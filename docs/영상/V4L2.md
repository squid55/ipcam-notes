# V4L2 (Video4Linux2)

> 리눅스 커널이 영상 입출력 장치를 다루기 위해 제공하는 API. `/dev/videoN` 파일을
> `ioctl` 로 제어한다.

## 왜 필요한가

카메라 작업의 **첫 관문**이다. 센서에서 픽셀이 나오는 것과 애플리케이션이 프레임을 받는 것
사이에 이 계층이 있고, 여기를 지나지 않는 경로는 대개 벤더 전용 SDK 다.

그래서 **벤더 SDK 없이 작업할 수 있는지가 V4L2 에서 갈린다.** 실측: 어떤 SoC 는 하드웨어
H.264 인코더를 별도 `/dev/videoN` 으로 올려두고 `S_FMT` 로 `H264` 를 지정하면 압축
스트림을 그대로 낸다. 그 경우 표준 도구가 전부 그대로 쓰인다. 반대로 벤더 API 만 노출하는
칩이면 작업량이 몇 배가 된다.

확인 비용이 낮으므로 SDK 문서를 파기 전에 먼저 열어보는 값이 있다.

## 최소 이해 수준

- **`/dev/videoN` 은 「카메라 한 대」가 아니다.** 파이프라인의 단계별로 여러 개가 생긴다.
  실측 예: `video0~3` = ISP 원시 출력, `video4` = H.264 인코더, `video5` = MJPEG 인코더.
  번호와 역할의 대응은 칩마다 다르고 문서에 없을 수도 있다.
- **포맷은 협상한다.** `ENUM_FMT` 로 목록을 받고 `S_FMT` 로 요청하고 `G_FMT` 로 실제 적용된
  값을 되읽는다. 요청과 결과가 다를 수 있으므로 되읽기를 생략하면 안 된다.
- **버퍼 흐름을 외운다.**
  `REQBUFS` → `QUERYBUF` → `mmap` → `QBUF` → `STREAMON` → (`DQBUF` ↔ `QBUF` 반복)
  → `STREAMOFF` → `munmap`
- **`read()` 가 항상 되는 것은 아니다.** 지원하지 않는 드라이버에서 `cat /dev/video0` 은
  `Invalid argument` 를 낸다. 그때는 `mmap` 방식만 가능하다.
- **픽셀 포맷은 FourCC 네 글자다.** `NV12` `YUYV` `MJPG` `H264` `HEVC`.
  압축 포맷도 같은 자리에 온다 — 즉 인코더 출력도 「픽셀 포맷」으로 표현된다.
- **압축 포맷에는 `sizeimage` 를 직접 정해줘야 한다.** 비압축은 해상도에서 계산되지만
  압축은 크기가 가변이라 드라이버가 추정한다. 안 정하면 경고가 뜨고 기본값이 쓰인다.

## 직접 해보기

### 1. 장치 목록과 능력

```bash
ls -l /dev/video*
v4l2-ctl --list-devices
v4l2-ctl -d /dev/video0 --all
```

`v4l2-ctl` 은 `v4l-utils` 패키지에 있다. **임베디드 보드에는 없는 경우가 많다** — 그럴 때는
직접 열어 `VIDIOC_QUERYCAP` 을 호출하는 20줄짜리 프로그램을 짜는 편이 빠르다.
이 프로젝트에서도 그렇게 했다(의존성 없는 정적 바이너리).

### 2. 지원 포맷 확인

```bash
v4l2-ctl -d /dev/video0 --list-formats-ext
```

여기에 `H264` 나 `MJPG` 가 보이면 **하드웨어 인코더가 표준 경로로 노출된 것**이다.
벤더 SDK 를 안 써도 될 가능성이 크다.

⚠ `ENUM_FRAMESIZES` 를 구현하지 않은 드라이버도 있다. 해상도 목록이 비어도 결함이 아니며,
`S_FMT` 로 직접 지정하면 동작하는 경우가 있다.

### 3. 실제로 프레임을 받아보기

```bash
v4l2-ctl -d /dev/video0 --set-fmt-video=width=1280,height=720,pixelformat=NV12 \
         --stream-mmap --stream-count=30 --stream-to=out.raw
ls -l out.raw
```

**프레임 크기를 확인하는 것이 핵심이다.**

```
1280 × 720 × 1.5 = 1,382,400 바이트  ← NV12 한 장
30장 → 41,472,000 바이트
```

압축을 요청했는데 이 값이 나오면 압축이 일어나지 않은 것이다. → [흔한 오해](#흔한-오해)

### 4. 살아 있는지 판정하기

```bash
# 휘도 평면의 표준편차를 본다 (NV12 의 앞 W×H 바이트가 Y)
python3 - <<'EOF'
import statistics
W,H=1280,720
d=open('out.raw','rb').read(W*H)
print('Y stddev =', round(statistics.pstdev(d),1))
EOF
```

표준편차가 0 에 가까우면 균일한 화면이다. **프레임 수만 세면 센서가 죽어도 「정상」으로
보인다** — ISP 가 검은 프레임을 규칙적으로 내보내기 때문이다.

## 더 들어가면

- **멀티플레인 API** (`V4L2_CAP_VIDEO_CAPTURE_MPLANE`) — Y 평면과 UV 평면을 별도 버퍼로
  받는다. 하드웨어가 평면별로 다른 메모리를 쓰는 경우에 필요하다.
- **DMABUF** — 버퍼를 CPU 로 복사하지 않고 인코더·GPU 에 그대로 넘긴다. 대역폭이 빠듯한
  임베디드에서 의미가 크다.
- **Media Controller API** (`/dev/mediaN`) — 센서 → ISP → 인코더 연결 관계를 런타임에
  바꾼다. 파이프라인이 고정된 칩에서는 노출되지 않을 수 있다.
- **컨트롤** (`VIDIOC_S_CTRL`) — 노출·게인·비트레이트 등. 벤더가 표준 컨트롤로 노출하는지
  전용 API 로만 열어두는지가 칩마다 다르다.

## 흔한 오해

### 「`MJPG` 라고 보고하면 압축된 것이다」

아니다. 드라이버가 요청을 받아들이고 `MJPG` 라고 보고하면서도 비압축 프레임을 주는 경우가
있다. **프레임 크기가 매번 동일하면 압축되지 않은 것으로 봐야 한다.**

### 「프레임이 오면 센서가 살아 있다」

아니다. 센서가 죽어도 ISP 는 검은 프레임을 규칙적으로 낸다.
휘도 표준편차를 함께 봐야 갈린다.

### 「`STREAMOFF` 는 바로 끝난다」

수 초 블로킹되는 경우가 있다. ISP 가 프레임을 채우는 중에 정지 명령이 겹친 것이다.
버퍼 재큐를 먼저 멈추고 진행 중인 프레임을 배출한 뒤 `STREAMOFF` 하면 해소된다.
스트리밍 서버에서 이 순서를 안 지키면 클라이언트가 끊길 때마다 그만큼 멈춘다.

### 「센서는 I2C 로 보이니 `i2cdetect` 로 확인하면 된다」

항상 아니다. I2C 버스를 별도 코프로세서(비디오코어 등)가 소유하고 리눅스 쪽에서는
비활성인 구성이 있다. 그 경우 `i2cdetect` 접근은 의미가 없고, 센서 설정은 벤더 파라미터
파일에서 지정한다.
