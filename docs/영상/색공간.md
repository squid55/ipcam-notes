# 색공간 · YUV · NV12

> 색을 숫자로 표현하는 방식. 영상 처리에서는 RGB 보다 YUV 계열을 훨씬 많이 쓴다.

## 왜 필요한가

카메라에서 나온 데이터를 받아 화면에 띄우거나 인코더에 넣으려면 **어떤 배열로 들어 있는지**
알아야 한다. 포맷을 잘못 알면 초록색 화면이나 두 겹으로 겹친 화면이 나온다.

그리고 **버퍼 크기 계산의 근거**다. 프레임 하나가 몇 바이트인지 알면 압축이 되고 있는지,
메모리가 얼마나 필요한지, 대역폭이 얼마인지가 바로 나온다.

## 최소 이해 수준

![NV12 메모리 배치. Y 평면 뒤에 UV 교차 평면이 붙는다. `stride` 와 `width` 는 다를 수 있다.](../fig/nv12.svg)

- **YUV 는 밝기와 색을 분리한다.**
  `Y` 는 밝기(휘도), `U`·`V` 는 색차다. 사람 눈이 밝기 변화에 민감하고 색 변화에는
  둔하기 때문에, **색 정보를 줄여도 잘 모른다.** 이것이 압축의 출발점이다.
- **크로마 서브샘플링 표기.**
  `4:4:4` 는 색을 안 줄인 것, `4:2:2` 는 가로로 절반, `4:2:0` 은 가로·세로 절반.
  카메라·코덱은 거의 `4:2:0` 이다.
- **바이트 수 계산.**
  ```
  4:4:4   W × H × 3
  4:2:2   W × H × 2
  4:2:0   W × H × 1.5
  ```
  1920×1080 4:2:0 → `1920 × 1080 × 1.5 = 3,110,400` 바이트.
- **평면(planar) vs 인터리브(packed).**
  평면은 `YYYY… UUUU… VVVV…` 처럼 따로 모아 두고, 인터리브는 픽셀마다 섞는다.
  같은 `4:2:0` 도 배치가 다르면 다른 포맷이다.
- **자주 만나는 것 넷.**

  | FourCC | 구조 | 비고 |
  |---|---|---|
  | `NV12` | Y 평면 + UV 교차 평면 | 하드웨어 인코더가 가장 많이 받는 형식 |
  | `I420` (`YU12`) | Y · U · V 세 평면 | 소프트웨어 처리에서 흔하다 |
  | `YUYV` (`YUY2`) | 4:2:2 인터리브 | USB 카메라에서 흔하다 |
  | `RGB24` / `BGR24` | 8비트 3채널 | OpenCV 기본은 `BGR` |

- **`NV12` 의 메모리 배치.**
  ```
  [0 .. W*H)              Y  (한 픽셀 1바이트)
  [W*H .. W*H*3/2)        UV (2×2 픽셀마다 U,V 한 쌍)
  ```
  즉 앞의 `W × H` 바이트만 떼면 그대로 흑백 영상이 된다.
- **스트라이드(stride)를 조심한다.**
  하드웨어가 줄 단위로 정렬을 요구하면 한 줄의 실제 바이트 수가 `W` 보다 크다.
  `1920` 폭인데 스트라이드가 `2048` 인 경우가 있다. 계산에 `W` 를 그대로 쓰면 화면이 기운다.

## 직접 해보기

### 1. NV12 파일에서 흑백 이미지 꺼내기

앞부분만 떼면 Y 평면이다. 별도 라이브러리 없이 확인된다.

```bash
W=1280; H=720
head -c $((W*H)) frame.nv12 > y.gray

# 보려면 (ImageMagick)
convert -size ${W}x${H} -depth 8 gray:y.gray y.png
```

영상이 보이면 포맷과 해상도를 맞게 짚은 것이다.
**깨지거나 기울어지면 스트라이드나 해상도가 다른 것이다.**

### 2. 프레임 크기로 포맷 역추정

```bash
ls -l frame.raw
python3 -c "
s=$(stat -c%s frame.raw); W,H=1280,720
for name,f in [('4:2:0',1.5),('4:2:2',2),('4:4:4',3),('RGB24',3)]:
    if abs(s - W*H*f) < 16: print('아마', name)"
```

받은 데이터가 무엇인지 문서가 없을 때 쓸 수 있다.

### 3. 변환해 보기

```bash
ffmpeg -f rawvideo -pix_fmt nv12 -s 1280x720 -i frame.nv12 -frames 1 out.png
ffmpeg -i out.png -pix_fmt yuv420p -f rawvideo i420.raw
ls -l frame.nv12 i420.raw   # 크기가 같다 — 배치만 다르다
```

`NV12` 와 `I420` 은 **같은 정보를 다르게 배치**한 것임이 크기로 확인된다.

### 4. 지원 포맷 목록 보기

```bash
ffmpeg -pix_fmts | head -30
v4l2-ctl -d /dev/video0 --list-formats
```

## 더 들어가면

- **색 범위(range).** `limited`(16~235)와 `full`(0~255). 잘못 맞추면 검은색이
  회색으로 보이거나 명암이 뭉친다.
- **색 공간 계수.** `BT.601`(SD) · `BT.709`(HD) · `BT.2020`(UHD).
  YUV↔RGB 변환식의 계수가 다르다. 섞으면 색이 미묘하게 틀어진다.
- **감마 · 전달 함수.** 센서의 선형 값을 사람 눈에 맞게 비선형으로 옮긴다.
  HDR 에서는 `PQ`·`HLG` 가 쓰인다.
- **베이어 패턴.** 센서에서 나오는 원시 데이터는 아직 YUV 도 RGB 도 아니다.
  → [이미지 센서](이미지센서.md)

## 흔한 오해

### 「YUV 는 압축 형식이다」

아니다. 비압축이다. 색 정보를 줄이는 것(서브샘플링)과 압축은 다른 단계다.
`NV12` 프레임은 여전히 3 MB 다.

### 「RGB 로 받아서 처리하면 편하다」

편하지만 대역폭이 두 배다. 그리고 카메라·인코더가 RGB 를 지원하지 않는 경우가 많아
중간에 변환이 끼어든다. 임베디드에서는 그 변환 비용이 무시할 수 없다.

### 「해상도만 알면 프레임 크기를 안다」

포맷과 스트라이드를 함께 알아야 한다. 같은 1280×720 이 921,600 · 1,382,400 ·
1,843,200 · 2,764,800 바이트일 수 있다.
