# 하드웨어 인코더 vs 소프트웨어 인코더

> 같은 H.264 를 만드는 두 가지 방법. SoC 안의 전용 회로가 하느냐,
> CPU 가 코드로 하느냐의 차이다.

## 왜 필요한가

임베디드 카메라에서 이것은 선택이 아니다. **소프트웨어 인코딩은 성능이 안 나온다.**
1080p30 H.264 를 `libx264` 로 돌리면 데스크톱 CPU 도 코어 하나를 다 먹는데,
카메라의 CPU 는 그 몇 분의 일이다.

그래서 하드웨어 인코더를 쓰는데, 그 순간 **할 수 있는 것이 크게 줄어든다.**
무엇이 되고 무엇이 안 되는지 미리 알아야 설계가 흔들리지 않는다.

## 최소 이해 수준

- **하드웨어 인코더는 고정 기능 블록이다.** SoC 안에 VPU · VENC 같은 이름으로 있다.
  전력을 거의 안 쓰고 CPU 를 거의 안 쓴다.
- **리눅스에서는 V4L2 M2M 으로 노출된다.** 입력 큐에 NV12 를 넣고 출력 큐에서
  H.264 바이트를 꺼내는 구조다. → [V4L2](../영상/V4L2.md)
- **압축 효율은 소프트웨어가 낫다.** 같은 비트레이트에서 `libx264 -preset slow` 가
  하드웨어보다 화질이 좋다. 하드웨어는 **탐색 범위와 모드 결정을 단순화**해서
  실시간을 맞추기 때문이다.
- **조절할 수 있는 것이 적다.** 비트레이트 · GOP 길이 · 프로파일 · 레벨 정도다.
  `x264` 의 수십 가지 옵션에 해당하는 것이 없다.
- **입력 형식이 고정이다.** 대개 `NV12` 하나만 받는다. 다른 형식이면
  변환이 필요하고, 그 변환을 CPU 로 하면 **인코더로 아낀 것을 도로 쓴다.**
- **동시 세션 수에 상한이 있다.** 하드웨어 블록이 하나면 시분할로 나눠 쓴다.
  해상도와 프레임레이트의 총합으로 한계가 정해진다.
- **제로 카피가 관건이다.** 센서 → ISP → 인코더가 **같은 메모리를 가리키게**
  만들면 복사가 사라진다. DMABUF 로 버퍼 핸들을 넘긴다.
  `mmap` 으로 읽어서 다시 쓰면 대역폭을 두 배로 쓴다.

## 비교

| | 하드웨어 | 소프트웨어 |
|---|---|---|
| CPU 사용 | 거의 없음 | 코어 하나 이상 |
| 전력 | 낮다 | 높다 |
| 화질 (같은 비트레이트) | 보통 | 좋다 |
| 지연 | 낮고 일정하다 | 설정에 따라 다르다 |
| 조절 범위 | 좁다 | 넓다 |
| 동시 세션 | 하드웨어 상한 | CPU 만큼 |
| 이식성 | SoC 마다 다르다 | 어디서나 같다 |
| 디버깅 | 어렵다 (블랙박스) | 쉽다 |

## 직접 해보기

### 1. 하드웨어 인코더가 있는지 찾기

```bash
# M2M 장치 목록
v4l2-ctl --list-devices

# 출력(인코더 입력) 쪽 형식 = 받아들이는 원본 형식
v4l2-ctl -d /dev/video11 --list-formats-out
# 캡처(인코더 출력) 쪽 형식 = 만들어 내는 압축 형식
v4l2-ctl -d /dev/video11 --list-formats
```

`out` 쪽에 `NV12`, `capture` 쪽에 `H264` 가 보이면 그것이 인코더다.

### 2. 조절 가능한 항목 전부 보기

```bash
v4l2-ctl -d /dev/video11 --list-ctrls-menus | grep -iA2 -E 'bitrate|gop|profile|level|h264'
```

**여기 없는 것은 조절할 수 없다.** 이 목록이 설계의 제약 조건이다.
`video_bitrate` 는 있는데 `h264_i_frame_qp` 가 없다면 QP 를 직접 못 만진다.

### 3. 비트레이트를 바꿔 실제로 반영되는지

```bash
v4l2-ctl -d /dev/video11 --set-ctrl=video_bitrate=6000000
v4l2-ctl -d /dev/video11 --get-ctrl=video_bitrate
```

설정은 받아들이는데 출력 크기가 안 바뀌는 경우가 있다.
**설정값이 아니라 결과 바이트를 재서 확인한다.**

```bash
timeout 10 <스트림 받기> -o /tmp/t.h264; ls -l /tmp/t.h264
# 파일크기 ÷ 10 × 8 = 실제 bps
```

### 4. CPU 사용량으로 어느 쪽이 일하는지 구분

```bash
# 스트리밍 중에
top -bn1 | head -15
```

인코딩 중인데 CPU 가 한 자릿수 퍼센트면 하드웨어가 일하는 것이다.
80% 를 넘으면 소프트웨어 경로로 떨어진 것이다 — **의도한 설정이 안 먹은 것**이다.

### 5. 화질 차이를 직접 재기

같은 비트레이트로 고정해서 비교한다.

```bash
ffmpeg -i src.mp4 -c:v libx264 -b:v 2M -preset slow -an sw.mp4
# 보드에서 같은 비트레이트로 하드웨어 인코딩한 파일을 hw.mp4 로 받아온다
ffmpeg -i sw.mp4 -i src.mp4 -lavfi ssim -f null -
ffmpeg -i hw.mp4 -i src.mp4 -lavfi ssim -f null -
```

### 6. 복사가 일어나는지 확인

```bash
# 메모리 대역폭이 병목이면 이쪽이 먼저 포화한다
vmstat 1 5
```

CPU 는 여유가 있는데 프레임이 떨어지면 **메모리 복사나 버스 대역폭**을 의심한다.

## 더 들어가면

- **V4L2 M2M 흐름.** `VIDIOC_S_FMT`(양쪽) → `REQBUFS`(양쪽) → `QBUF` → `STREAMON` →
  `DQBUF`. 큐가 둘이라 코드가 캡처보다 복잡하다.
- **DMABUF 임포트.** 캡처 장치에서 받은 버퍼 fd 를 인코더에 그대로 넘긴다.
  이것이 되면 CPU 가 픽셀을 한 번도 만지지 않는다.
- **IDR 강제 요청.** 새 클라이언트가 붙었을 때 키프레임을 즉시 만들게 하는 제어.
  `V4L2_CID_MPEG_VIDEO_FORCE_KEY_FRAME`. 없으면 새 시청자가 **다음 GOP 까지 기다린다.**
- **듀얼·트리플 스트림.** 하나는 고해상도 녹화용, 하나는 저해상도 미리보기용.
  인코더가 동시 세션을 지원하는지, 아니면 스케일러로 나눠 순차 처리하는지 확인한다.
- **벤더 전용 API.** V4L2 대신 독자 SDK 만 주는 SoC 도 있다.
  그 경우 이식성이 사라지고 **소스 없는 라이브러리에 묶인다.**
  부품 선택 단계에서 표준 인터페이스 지원 여부를 보는 것이 낫다.
- **GPU 인코더와의 차이.** 데스크톱의 NVENC · QSV · VAAPI 도 하드웨어 인코더다.
  성격은 같고, 조절 범위가 임베디드보다 넓은 편이다.

## 흔한 오해

### 「하드웨어 인코더가 소프트웨어보다 좋다」

빠르고 전력이 적은 것과 화질이 좋은 것은 다르다. 같은 비트레이트라면
잘 튜닝한 소프트웨어가 대개 이긴다. **하드웨어를 쓰는 이유는 화질이 아니라
실시간과 전력**이다.

### 「비트레이트만 올리면 화질이 해결된다」

대개 맞지만 한계가 있다. 하드웨어 인코더가 탐색을 단순화한 부분은
비트를 더 줘도 메워지지 않는다. 그리고 회선과 저장 용량이 비용으로 돌아온다.

### 「인코더가 지원하는 최대 해상도까지 다 쓸 수 있다」

「1080p60 또는 4K30」처럼 **총 처리량으로 상한이 정해진다.**
동시 스트림을 여러 개 쓰면 그 합이 상한 안에 들어야 한다.
데이터시트의 최대 해상도는 단일 스트림 기준이다.

### 「입력 형식은 변환하면 된다」

변환 비용이 인코딩 비용보다 클 수 있다. 1080p30 을 CPU 로 색변환하면
그 자체로 코어 하나를 먹는다. **파이프라인 전체가 같은 형식을 쓰게** 맞추는 편이
훨씬 싸다.

### 「지연이 낮으니 하드웨어가 유리하다」

인코더 지연은 전체의 일부다. ISP 버퍼 · 인코더 큐 · 네트워크 버퍼 · 디코더
지터 버퍼가 다 합쳐진다. 인코더만 최적화해도 전체가 크게 줄지 않는다.
→ [RTP](../네트워크/RTP.md)
