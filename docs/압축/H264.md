# H.264 (AVC)

> 블록 기반 하이브리드 방식의 영상 압축 표준. ITU-T H.264 와 ISO/IEC MPEG-4 Part 10 이
> 같은 규격이다.

## 왜 필요한가

압축하지 않으면 회선이 버티지 못한다. 계산해 보면 명확하다.

```
1920 × 1080 × 1.5바이트(NV12) × 30fps = 초당 93 MB = 747 Mbps
```

100 Mbps 이더넷에 한 대도 못 올린다. H.264 로 압축하면 같은 영상이 **4~8 Mbps** 가 된다.
즉 100 배 이상 줄인다.

IP카메라에서는 거의 항상 하드웨어 인코더가 이 일을 한다. 그래서 개발자가 다루는 것은
「압축 알고리즘」이 아니라 **인코더를 어떻게 설정하고 그 출력을 어떻게 전송하는가** 다.

## 최소 이해 수준

- **I / P / B 프레임.**
  `I` 는 혼자서 복원되는 프레임, `P` 는 앞을 참조, `B` 는 앞뒤를 참조한다.
  `B` 는 압축률이 좋지만 **뒤 프레임을 기다려야 하므로 지연이 생긴다.**
  실시간 감시에서는 `B` 를 안 쓰는 구성이 흔하다.
- **GOP (Group of Pictures).**
  `I` 프레임 간격. 짧으면 채널 진입이 빠르고 오류 복구가 쉽지만 비트레이트가 커진다.
  긴 GOP 는 접속 직후 화면이 늦게 뜨는 원인이 된다.
- **NAL 단위.**
  H.264 스트림은 NAL(Network Abstraction Layer) 단위의 나열이다.
  바이트 스트림에서는 `00 00 00 01`(또는 `00 00 01`) 시작 코드로 구분된다.
  다음 바이트의 하위 5비트가 타입이다 — `1`=non-IDR, `5`=IDR, `7`=SPS, `8`=PPS.
- **SPS / PPS 없이는 디코딩이 시작되지 않는다.**
  해상도·프로파일·참조 구조가 여기 들어 있다. 디코더는 이것을 먼저 받아야 한다.
- **Annex B vs AVCC.**
  같은 데이터를 두 방식으로 감싼다. Annex B 는 시작 코드로 구분(파일·RTP),
  AVCC 는 길이 접두어로 구분(MP4 컨테이너). **섞으면 디코더가 아무것도 못 읽는다.**
- **프로파일과 레벨.**
  프로파일은 쓰는 기능의 범위(Baseline · Main · High), 레벨은 해상도·비트레이트 상한이다.
  `High / L4.0` 이면 1080p30 정도까지다.
- **레이트 컨트롤.**
  `CBR` 은 비트레이트를 고정해 회선 계획이 쉽고, `VBR` 은 장면에 따라 변동한다.
  화질은 결국 **비트레이트가 제약**한다 — 해상도를 올리고 비트레이트를 그대로 두면
  화질이 떨어진다.

## 직접 해보기

### 1. 스트림 구조 보기

```bash
ffprobe -v error -show_streams out.h264
```

`codec_name`·`profile`·`level`·`width`·`height` 를 확인한다.
`profile` 이 나오면 SPS 를 정상적으로 읽은 것이다.

### 2. NAL 타입을 직접 세기

시작 코드를 찾아 타입을 세면 스트림 구조가 보인다.

```bash
python3 - <<'EOF'
d=open('out.h264','rb').read()
i=0; seq=[]
while True:
    j=d.find(b'\x00\x00\x00\x01', i)
    if j<0: break
    seq.append(d[j+4] & 0x1f)
    i=j+4
from collections import Counter
print('NAL 개수', len(seq))
print('타입 분포', Counter(seq).most_common())
print('앞 40개   ', seq[:40])
EOF
```

`7`(SPS)·`8`(PPS)·`5`(IDR) 이 **일정 간격으로 반복**되는지 본다.
실측: 어떤 인코더는 32프레임마다 `SPS → PPS → IDR` 을 다시 끼워 넣는다.
그래서 스트림 선두에 파라미터셋이 없어도 중간부터 붙는 클라이언트가 디코딩할 수 있다.

### 3. 실제 비트레이트 측정

```bash
# 10초 받아 크기를 본다
ls -l out.h264
python3 -c "
import os; s=os.path.getsize('out.h264')
print(f'{s} bytes / 10s = {s*8/10/1e6:.2f} Mbps')"
```

설정한 목표 비트레이트와 비교한다. 크게 벗어나면 레이트 컨트롤이 다른 채널과
묶여 있는지 의심한다.

### 4. 프레임별 크기 분포

```bash
ffprobe -v error -select_streams v -show_frames \
        -show_entries frame=pict_type,pkt_size out.h264 | \
  grep -E "pict_type|pkt_size" | paste - - | head -20
```

`I` 프레임이 `P` 프레임보다 몇 배 큰지 보인다. 이 비율이 GOP 설정의 효과다.
**모든 프레임 크기가 같으면 압축이 안 된 것이다.**

## 더 들어가면

- **CABAC vs CAVLC** — 엔트로피 코딩 방식. CABAC 이 압축률이 좋지만 연산이 무겁다.
  Baseline 프로파일은 CABAC 을 쓰지 않는다.
- **슬라이스** — 한 프레임을 여러 조각으로 나눠 병렬 처리·오류 격리에 쓴다.
- **참조 프레임 개수** — 많으면 압축률이 오르고 메모리와 지연이 늘어난다.
- **SEI** — 타임스탬프 등 부가 정보. 카메라가 프레임 시각을 여기 넣는 경우가 있다.

## 흔한 오해

### 「선두에 SPS/PPS 가 없으면 빠진 것이다」

아니다. 주기적으로 재삽입되는 구성이 많다. NAL 을 전수 세어 확인해야 한다.
선두만 보고 「파라미터셋을 따로 넣어줘야 한다」고 결론 내리면 불필요한 작업이 생긴다.

### 「해상도를 올리면 화질이 좋아진다」

비트레이트가 그대로면 오히려 나빠진다. 같은 비트를 더 많은 픽셀에 나눠 쓰기 때문이다.
해상도·프레임레이트·비트레이트는 셋을 함께 정해야 한다.

### 「H.265 가 항상 낫다」

압축률은 낫지만 연산량이 크고 라이선스 구조가 복잡하며, 받는 쪽(NVR·브라우저)이
지원하지 않으면 쓸 수 없다. 감시 시장에서 H.264 가 오래 남는 이유다.

### 「인코더 설정에 화질 계수가 있으면 그게 화질이다」

인코더가 QP(양자화 계수)를 노출하지 않고 **비트레이트로만 제어**하는 경우가 있다.
그때는 「화질」 설정이 내부적으로 비트레이트 환산으로 구현된다 —
계수가 낮으면 비트레이트가 낮아지고, 하한 아래로 가면 레이트 컨트롤이 진동한다.
