# H.265 (HEVC) — H.264 와의 차이

> H.264 의 후속 규격. 같은 화질을 대략 절반의 비트레이트로 낸다.
> 대신 계산량이 늘고 특허 문제가 복잡하다.

## 왜 필요한가

4K 카메라를 H.264 로 내보내면 비트레이트가 회선과 저장장치를 압박한다.
감시 시스템은 카메라 수십 대를 24시간 녹화하므로 **저장 비용이 곧 제품 경쟁력**이다.
절반이면 저장 기간이 두 배가 된다.

그래서 4K 이상 제품은 H.265 가 기본이 됐다. 다만 낡은 클라이언트가 못 받는 경우가 있어
**H.264 스트림을 함께 내보내는 구성**이 흔하다.

## 최소 이해 수준

- **구조의 틀은 같다.** 블록 단위 예측 → 변환 → 양자화 → 엔트로피 부호화.
  I/P/B 프레임, GOP, 레이트 컨트롤 개념이 그대로 통한다. → [H.264](H264.md)
- **블록이 커지고 유연해졌다.**
  H.264 의 매크로블록은 16×16 고정인데, H.265 는 **CTU 64×64** 에서 시작해
  쿼드트리로 쪼갠다. 평평한 하늘은 큰 블록 하나로 끝나므로 헤더 비용이 줄어든다.
  **고해상도일수록 이득이 커지는 이유**가 이것이다.
- **화면 내 예측 방향이 9 → 35 개.** 비스듬한 경계를 더 잘 맞춘다.
- **필터가 하나 늘었다.** 디블로킹 뒤에 **SAO**(Sample Adaptive Offset)가 붙어
  링잉과 밴딩을 줄인다.
- **엔트로피 부호화는 CABAC 하나로 통일됐다.** H.264 의 CAVLC 같은 대안이 없다.
- **NAL 헤더가 1바이트 → 2바이트.** 파싱 코드를 그대로 쓸 수 없다.
- **파라미터 세트가 셋이다.** H.264 의 SPS·PPS 에 **VPS**(Video Parameter Set)가 더해진다.
- **타일과 슬라이스 세그먼트.** 화면을 격자로 나눠 병렬 처리한다.
  하드웨어 구현과 다중 코어 디코딩에 유리하다.
- **프로파일 이름이 다르다.** `Main` · `Main10` · `Main Still Picture`.
  `Main10` 이 10비트를 지원하고, 밴딩이 적어 어두운 장면에 유리하다.

## H.264 와 비교

| | H.264 (AVC) | H.265 (HEVC) |
|---|---|---|
| 규격 | ITU-T H.264 / MPEG-4 Part 10 | ITU-T H.265 / MPEG-H Part 2 |
| 기본 블록 | 매크로블록 16×16 | CTU 최대 64×64, 쿼드트리 분할 |
| 화면 내 예측 | 9 방향 | 35 방향 |
| 루프 필터 | 디블로킹 | 디블로킹 + SAO |
| 파라미터 세트 | SPS, PPS | VPS, SPS, PPS |
| NAL 헤더 | 1바이트 | 2바이트 |
| 인코딩 부하 | 기준 | 대략 2~10배 |
| 비트레이트 | 기준 | 같은 화질에서 40~50% 절감 |
| 브라우저 지원 | 사실상 전부 | 제한적 (아래 참고) |

## 직접 해보기

### 1. 같은 화질에서 비트레이트 비교

**품질 기준(CRF)을 고정**하고 결과 크기를 재는 것이 옳은 비교다.
비트레이트를 고정해 놓고 비교하면 무엇을 본 것인지 알 수 없다.

```bash
ffmpeg -y -i src.mp4 -c:v libx264 -crf 23 -an h264.mp4
ffmpeg -y -i src.mp4 -c:v libx265 -crf 28 -an h265.mp4
ls -l h264.mp4 h265.mp4
```

⚠ **CRF 값의 의미가 코덱마다 다르다.** `x265` 의 28 이 `x264` 의 23 에 대략 대응한다.
같은 숫자를 넣으면 비교가 성립하지 않는다.

객관 지표까지 보려면:

```bash
ffmpeg -i h265.mp4 -i src.mp4 -lavfi ssim -f null -
ffmpeg -i h264.mp4 -i src.mp4 -lavfi ssim -f null -
```

### 2. 인코딩 시간 비교

```bash
time ffmpeg -y -i src.mp4 -c:v libx264 -crf 23 -an /dev/null
time ffmpeg -y -i src.mp4 -c:v libx265 -crf 28 -an /dev/null
```

**차이가 이 기술의 진짜 비용이다.** 임베디드에서 소프트웨어 H.265 는 현실적이지 않다.

### 3. NAL 구조 확인

```bash
ffmpeg -i src.mp4 -c:v libx265 -crf 28 -an -f hevc out.h265
ffmpeg -i out.h265 -c copy -bsf:v trace_headers -f null - 2>&1 | head -60
```

`VPS` · `SPS` · `PPS` 가 순서대로 보인다. H.264 에는 `VPS` 가 없다.

### 4. 하드웨어 인코더가 H.265 를 지원하는지

```bash
v4l2-ctl -d /dev/video11 --list-formats-out | grep -iE 'HEVC|H265|H264'
```

`HEVC` 가 목록에 있으면 SoC 가 지원하는 것이다. 없으면 소프트웨어뿐이고,
그것은 실시간으로 불가능한 경우가 많다. → [하드웨어 인코더 vs 소프트웨어](하드웨어인코더.md)

### 5. 브라우저가 재생하는지

```js
console.log(MediaSource.isTypeSupported('video/mp4; codecs="hvc1.1.6.L93.B0"'));
console.log(MediaSource.isTypeSupported('video/mp4; codecs="avc1.640028"'));
```

`false` 가 나오면 그 브라우저에서는 못 튼다. **웹 미리보기는 H.264 나 MJPEG 로
따로 내보내야 하는 이유**가 여기 있다. → [MJPEG](MJPEG.md)

## 더 들어가면

- **H.265 특허.** 여러 특허 풀이 나뉘어 있어 라이선스 구조가 복잡하다.
  이 때문에 웹 진영이 채택을 미뤘고, **AV1** 과 **VP9** 같은 무료 대안이 나왔다.
  제품에 넣을 때는 SoC 벤더가 라이선스를 포함했는지 확인이 필요하다.
- **H.266 (VVC)** — 다음 세대. 다시 절반을 목표로 한다.
  2026년 현재 감시 카메라에서는 아직 드물다.
- **AV1** — 로열티 프리. 하드웨어 인코더 지원이 늘고 있지만
  임베디드 SoC 에는 아직 흔하지 않다.
- **Smart Codec / 지능형 코덱.** 감시 카메라 벤더가 붙이는 이름으로,
  규격 밖의 기법이 아니라 **관심 영역(ROI)에 비트를 더 주고 배경을 줄이는**
  레이트 컨트롤 튜닝이다. 정지 장면에서 GOP 를 늘리는 것도 여기 포함된다.
- **10비트의 실익.** `Main10` 은 밴딩이 줄어 **어두운 장면과 그라데이션**에서 눈에 띈다.
  대역폭은 크게 안 늘고 오히려 압축 효율이 좋아지는 경우도 있다.

## 흔한 오해

### 「H.265 가 항상 절반이다」

콘텐츠에 따라 다르다. 고해상도 · 평평한 영역이 많은 영상에서 이득이 크고,
저해상도 · 잡음 많은 영상에서는 차이가 작다. 실제로 재봐야 한다.

### 「H.265 로 바꾸면 CPU 만 조금 더 쓴다」

디코딩도 무겁다. 카메라 쪽은 하드웨어 인코더로 해결되지만
**관제 PC 가 32채널을 동시에 디코딩**해야 하면 그쪽이 먼저 한계에 닿는다.
카메라만 보고 결정할 일이 아니다.

### 「H.264 파서를 조금 고치면 H.265 도 읽는다」

NAL 헤더 크기와 파라미터 세트 구성이 다르다. 슬라이스 헤더 구조도 다르다.
**조금 고치는 것으로 끝나지 않는다.**

### 「최신 규격이니 호환성은 시간이 해결한다」

감시 시스템은 기존 녹화 서버와 붙어야 한다. 서버가 H.265 를 못 받으면
카메라만 새것이어도 쓸 수 없다. **듀얼 스트림으로 두 코덱을 함께 내는 구성**이
현실적인 답인 경우가 많다.
