# 인증과 인가 (Authentication · Authorization)

> 인증은 「누구인지 확인」하는 것, 인가는 「무엇을 할 수 있는지 결정」하는 것.
> 둘은 순서가 있고 섞으면 안 된다.

## 왜 필요한가

채용 공고에는 한 줄로 지나간다 — 「Authentication, Authorization 등 네트워크 보안 기술에
대한 이해」. 그런데 제품에서는 이것이 기능의 절반이다. 영상을 잘 보내는 것보다
**아무나 못 보게 하는 것**이 어렵다.

그리고 감시 장비는 여기가 뚫리면 피해가 곧바로 사생활 침해가 된다.
실제 사고 사례가 대부분 이 계층에서 나온다 — 기본 비밀번호, 인증 없는 경로,
세션이 끝나지 않는 문제.

## 최소 이해 수준

- **순서가 있다.** 인증 → 인가. 누구인지 모르면 무엇을 허용할지 정할 수 없다.
- **비밀번호를 저장하지 않는다.**
  단방향 해시 + **기기별 솔트** + **느린 반복**을 쓴다.
  `PBKDF2`·`bcrypt`·`scrypt`·`Argon2`. 반복 횟수가 공격 비용을 결정한다.
  `SHA-256` 한 번은 저장용으로 부족하다 — 너무 빠르다.
- **세션은 발급하고 만료시킨다.**
  로그인 후 토큰을 주고, 유휴 시간이 지나면 끊는다.
  토큰은 예측 불가능해야 하므로 **암호학적 난수 생성기**로 만든다.
  셸의 `$RANDOM` 이나 시각 기반 값은 쓰면 안 된다.
- **인가는 「무엇을」과 「누가」를 나눠 적는다.**
  역할 기반(RBAC)이 흔하다. 사용자에게 역할을, 역할에 권한을 붙인다.
  권한 축을 기능 단위로 쪼개야 「업무에 맞게」 줄 수 있다.
- **실패를 세고 잠근다.**
  연속 실패가 일정 횟수를 넘으면 일정 시간 막는다.
  **영구 잠금은 가용성 공격 수단이 되므로** 시간이 지나면 풀려야 한다.
- **실패 사유를 자세히 알려주지 않는다.**
  「아이디가 없습니다」와 「비밀번호가 틀렸습니다」를 구분해 주면
  계정 존재를 열거할 수 있다.
- **기본 계정·기본 비밀번호를 두지 않는다.**
  이미지에 박아두면 전 제품이 같은 값으로 나간다.
  최초 설정 때 기기마다 다른 값을 만들거나 변경을 강제한다.

## 직접 해보기

### 1. 인증 없이 접근하면 막히는지

```bash
# 관리 API 에 자격증명 없이 접근
curl -sk -o /dev/null -w '%{http_code}\n' https://<주소>/cgi-bin/status.cgi
```

`401` 이어야 한다. `200` 이면 그 경로는 인증 밖에 있다.

**모든 경로를 훑어야 한다.** 하나만 빠져 있어도 그것이 통로가 된다.

### 2. 세션 유휴 만료를 실제로 재보기

```
① 로그인한다
② 아무것도 누르지 않고 만료 시간 + 여유만큼 기다린다
③ 아무 기능을 눌러본다  → 로그인 화면으로 돌아가야 한다
```

⚠ **브라우저 탭을 열어둔 채 기다리면 안 된다.** 화면이 주기적으로 서버에 무언가를
물어보면 세션이 계속 갱신된다. 시험 전에 「주기 요청이 있는지」를 코드에서 확인해야
시험이 성립한다.

⚠ **긴 연결도 함정이다.** 실측: 영상 스트림이 한 번 인증을 통과한 뒤 다시 확인하지
않는 구조였다. 관리 화면은 잠기는데 **영상은 31분이 지나도 흐르고 있었다.**
「자리를 비운 단말」이라는 위험이 그대로 남는다.

고칠 때 또 함정이 있다 — 스트림이 세션 검사를 주기적으로 호출하면서 **갱신까지 하면**
아무도 손대지 않아도 세션이 영원히 살아난다. 유휴 만료를 넣으려다 없애는 셈이다.
**확인만 하고 갱신하지 않는 검사기**를 따로 둬야 한다.

### 3. 잠금을 시험하는 올바른 방법

틀린 비밀번호를 정해진 횟수만큼 넣어 잠기는 것까지는 절반이다.

```
④ 잠긴 상태에서 올바른 비밀번호를 넣는다  → 여전히 막혀야 한다
```

**이것이 핵심이다.** 「5회 실패하면 잠긴다」만 확인하면
「비밀번호가 틀렸다」와 구별되지 않는다.

⚠ 관리자 계정으로 시험하면 스스로 잠긴다. 일반 계정으로 한다.
그리고 잠금 창 안에 ④까지 끝내야 한다 — 늦으면 풀려서 그냥 로그인된다.

응답을 구분할 수 있으면 더 확실하다. 실측 예: 잠금이 성립하는 순간의 응답은
남은 시간이 고정값(300)이고, 잠금 중 재시도의 응답은 **남은 시간이 줄어든다**.
후자가 나오면 인증을 시도하기 **전에** 거부된 것이다.

### 4. 비밀번호 정책을 규칙별로 시험

규칙 하나씩만 위반하는 값을 만든다. 나머지는 다 만족시켜야 **그 규칙이 동작하는지**
확인된다.

```
abc123        길이 미달
abcdefghi     문자 종류 부족
Abcdefgh1     특수문자 없음
Kxxx7#mQv     같은 문자 3연속  (다른 조건은 모두 만족)
Abcd1234!     순차 나열        (다른 조건은 모두 만족)
```

### 5. 저장 형태 확인

```bash
# 자격증명 파일에 비밀번호 원문이나 단순 해시가 있는지
sudo cat <자격증명 파일>
```

솔트와 반복 횟수가 함께 저장돼 있어야 한다. 원문이 보이면 즉시 문제다.

## 더 들어가면

- **HTTP Digest 인증** — 비밀번호를 평문으로 보내지 않는 챌린지·응답 방식.
  RFC 2617 은 MD5 계열이고 RFC 7616 이 SHA-256 을 추가했다.
  응답 헤더에 `algorithm`·`qop` 가 없으면 옛 규격이다.
- **토큰 기반 인증(JWT 등)** — 서버가 상태를 갖지 않는 방식.
  만료·폐기 처리가 세션보다 까다롭다.
- **중복 접속 처리** — 같은 계정의 기존 세션을 끊는지, 새 접속을 막는지.
  운영 정책이므로 제품마다 다르다.
- **감사기록과의 연결** — 인증 성공·실패·잠금이 모두 기록돼야 사후 추적이 된다.
  기록 자체가 위변조되지 않아야 의미가 있다.
- **최소 권한 원칙** — 기본값을 「아무것도 못 함」으로 두고 필요한 것만 더한다.
  반대로 만들면 무엇이 열려 있는지 아무도 모르게 된다.

## 흔한 오해

### 「로그인이 되면 인증은 끝이다」

시작이다. 세션이 언제 끝나는지, 긴 연결이 언제 재확인하는지, 권한이 요청마다
확인되는지가 남는다. 실측으로 드러난 문제들이 대부분 **로그인 이후**에 있었다.

### 「해시를 쓰면 안전하다」

빠른 해시는 안전하지 않다. GPU 로 초당 수십억 번 시도할 수 있다.
솔트로 사전 계산(레인보우 테이블)을 막고, 반복으로 시도 비용을 올린다.

### 「인가는 화면에서 버튼을 숨기면 된다」

화면은 요청을 보내는 여러 방법 중 하나다. 브라우저를 거치지 않는 요청이 오면
그대로 통과한다. **권한 검사는 서버에서 해야 한다.**

같은 이유로 입력값 검사도 서버에서 해야 한다. 실측: 관리 단말 IP 허용목록에서
「현재 접속 IP 를 지울 수 없다」는 검사를 화면에만 두면, 우회 요청 한 번으로
기기에 접근할 수 없게 만들 수 있다.

### 「사유를 알려주면 안 되니 아무것도 말하지 않는다」

둘을 구분해야 한다.

```
인증 실패      사유를 자세히 알리지 않는다   (계정 열거 방지)
정책 위반      사유를 정확히 알려야 한다     (사용자가 고칠 수 있게)
```

실측: 비밀번호 거부 사유가 여섯 가지인데 화면이 늘 같은 문장을 냈다.
그 결과 **화면이 요구한 조건을 모두 지킨 값이 거부되면서 같은 안내가 반복**됐다.
사용자는 기기가 고장 났다고 여기거나, 될 때까지 아무 값이나 넣다가
**더 약한 비밀번호에 정착한다.** 거부는 옳았고 이유를 말하지 못한 것이 문제였다.

### 「검사 논리를 화면에도 넣으면 사용자 경험이 좋아진다」

두 벌로 구현하면 언젠가 갈라진다. 그때 화면은 통과라는데 기기는 거부하는 상태가 되고,
그건 안내가 없는 것보다 나쁘다.

**판정은 한 곳에서 하고, 화면은 그 결과를 받아 표시**해야 한다.
사유를 표시하려면 판정하는 쪽이 사유를 돌려주게 만든다.
