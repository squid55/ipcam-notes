# TLS · X.509 인증서

> TLS 는 통신을 암호화하고 상대를 확인하는 표준. X.509 는 그 확인에 쓰는 인증서 형식이다.

## 왜 필요한가

IP카메라에서 평문 통신은 선택지가 아니다. 관리 접속(웹)·영상 전송(RTSPS)·
로그 전송이 모두 TLS 위에 올라간다.

그런데 **암호화만으로는 부족하다.** 상대가 진짜 그 기기인지 확인하지 못하면
중간자가 자기 키로 연결을 받아 그대로 중계한다. 그 확인을 인증서가 한다.

기기 쪽에서 다뤄야 하는 일은 셋이다 — **인증서를 만들고, 서비스에 물리고,
바뀔 때 안전하게 교체하는 것.**

## 최소 이해 수준

- **핸드셰이크가 하는 일.**
  프로토콜 버전과 암호군을 정하고, 서버 인증서를 확인하고, 세션 키를 합의한다.
  TLS 1.3 은 왕복을 줄이고 옛 암호군을 제거했다.
- **버전.**
  1.0·1.1 은 폐기됐다. **제품에서는 빌드 단계에서 아예 빼는 것이 확실하다** —
  설정으로 끄면 설정이 되돌아갈 수 있다.
- **인증서에 들어 있는 것.**
  주체(Subject)·발급자(Issuer)·유효기간·공개키·확장(Extensions).
  확장 중 **SAN(Subject Alternative Name)** 이 실질적인 이름 검증 대상이다.
- **CN 이 아니라 SAN 을 본다.**
  현대 클라이언트는 `Subject` 의 CN 을 무시하고 SAN 만 본다.
  IP 로 접속하면 SAN 에 `IP:주소` 가, 도메인이면 `DNS:이름` 이 있어야 한다.
- **체인 검증과 이름 검증은 별개다.**
  「이 CA 가 발급했는가」와 「이 이름에 발급됐는가」는 다른 검사다.
  둘 다 해야 한다. → [흔한 오해](#체인만-검증하면-충분하다)
- **자체 서명과 사설 CA.**
  자체 서명은 그 인증서 자체를 신뢰 목록에 넣어야 한다(핀 고정에 가깝다).
  사설 CA 는 CA 하나만 배포하면 아래 인증서를 모두 신뢰한다 — 편하지만
  **그 CA 가 발급한 다른 인증서도 전부 통과한다.**
- **키 쌍은 기기마다 달라야 한다.**
  이미지에 키를 박으면 한 대가 뚫리면 전부 뚫린다.
  최초 설정 때 기기 안에서 생성하는 것이 원칙이다.

## 직접 해보기

### 1. 서버가 내놓는 인증서 보기

```bash
openssl s_client -connect <주소>:443 -showcerts </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

확인할 것 — `notBefore`/`notAfter` 가 현재를 포함하는가, SAN 에 접속에 쓴 주소가 있는가.

### 2. 프로토콜과 암호군

```bash
openssl s_client -connect <주소>:443 -brief </dev/null
```

`TLSv1.3` 과 AEAD 계열 암호군을 기대한다.

### 3. 옛 프로토콜이 막혀 있는지

```bash
openssl s_client -connect <주소>:443 -tls1_1 </dev/null 2>&1 | tail -3
```

거부되어야 한다.

⚠ **「거부됨」이 서버 설정이 아닐 수 있다.** 호스트의 `openssl` 이 옛 프로토콜을
제거한 판본이면 도구가 먼저 못 보낸다. 그 경우 출력에 `no protocols available` 류가 뜬다.
**서버의 성질과 내 도구의 한계를 구분해야** 잘못된 결론이 남지 않는다.

### 4. 이름 검증까지 확인

```bash
# 도메인
openssl s_client -connect <호스트>:443 -verify_hostname <호스트> </dev/null 2>&1 | grep -i verify

# IP 로 접속하는 경우 — 플래그가 다르다
openssl s_client -connect <IP>:443 -verify_ip <IP> </dev/null 2>&1 | grep -i verify
```

⚠ IP 에 `-verify_hostname` 을 쓰면 CN·DNS-SAN 과 대조해 **엉뚱한 실패**가 난다.
IP 는 `-verify_ip` 다. 이 구분을 몰라 「이름 불일치」로 오진하기 쉽다.

### 5. 인증서와 키가 짝인지

```bash
openssl x509 -noout -pubkey -in server.crt | openssl sha256
openssl pkey -pubout -in server.key        | openssl sha256
```

두 해시가 같아야 짝이다.

⚠ **웹서버의 설정 검사 기능을 믿으면 안 된다.** 실측: `lighttpd -t` 는 개인키와
인증서가 맞지 않아도, 인증서 자리에 아무 텍스트 파일을 넣어도 `Syntax OK` 를 낸다.
문법만 보기 때문이다. 확인하려면 **임시 포트로 실제 기동해 보는 수밖에 없다.**

### 6. 직접 만들어 보기 (SAN 포함)

```bash
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 \
  -sha256 -days 365 -nodes \
  -keyout server.key -out server.crt \
  -subj "/CN=192.168.0.10" \
  -addext "subjectAltName=IP:192.168.0.10,DNS:localhost"
openssl x509 -noout -text -in server.crt | grep -A1 "Alternative"
```

`-addext` 를 빼면 SAN 없는 인증서가 만들어지고, 요즘 클라이언트는 그것을 거부한다.
**시험용 인증서를 만들 때 가장 흔히 빠뜨리는 부분이다.**

## 더 들어가면

- **키 용도(KeyUsage)·확장 키 용도(EKU).**
  서버 인증서는 `serverAuth` 가 필요하다. ECDSA 키는 `keyEncipherment` 를 쓸 수 없어
  `digitalSignature` 만 넣는다 — 넣으면 일부 클라이언트가 거부한다.
- **CSR 흐름.**
  기기가 키를 만들고 CSR 을 내보내 외부 CA 가 서명한다. **개인키가 기기를 떠나지 않는다**는
  것이 이 방식의 요점이다.
- **폐기(CRL · OCSP).**
  유출된 인증서를 무효화하는 수단. 임베디드에서는 검사 비용과 가용성 때문에
  적용이 까다롭다.
- **mTLS(양방향 인증).**
  클라이언트도 인증서를 내놓는다. 카메라–NVR 연동을 기기 단위로 제한할 수 있다.
- **시각 의존성.**
  유효기간 판정이 시스템 시각에 달렸다. → [흔한 오해](#시계가-틀려도-tls-는-된다)

## 흔한 오해

### 「체인만 검증하면 충분하다」

아니다. 실측: 로그 전송 클라이언트가 `SSL_get_verify_result` 로 체인만 확인하고
이름 검증을 하지 않은 상태였다. 그러면 **같은 CA 가 발급한 다른 이름의 인증서로도
통과한다.** 사설 CA 를 쓰는 현장에서 그 CA 의 아무 인증서나 가진 쪽이 수집 서버를
사칭할 수 있다는 뜻이다.

OpenSSL 에서는 체인 검증과 별도로 이름을 걸어줘야 한다.

```c
X509_VERIFY_PARAM *vp = SSL_get0_param(ssl);
if (X509_VERIFY_PARAM_set1_ip_asc(vp, host) != 1)
    X509_VERIFY_PARAM_set1_host(vp, host, 0);
```

순서가 중요하다. IP 문자열을 `set1_host` 에 넣으면 DNS-SAN 과 대조해 엉뚱하게 판정한다.

### 「시계가 틀려도 TLS 는 된다」

안 된다. 유효기간 판정이 시스템 시각에 달렸다.

실측: 배터리 없는 보드가 1970년으로 부팅한 상태에서 인증서를 발급하면
`notBefore` 가 1970 이 되어 클라이언트가 만료로 거부한다.
그리고 **정상 서명된 펌웨어 업데이트조차** `certificate is not yet valid` 로 거부된다 —
서명자 인증서의 `notBefore` 가 미래로 보이기 때문이다.

발급 시점에 시각 하한을 두거나, 부팅 시 신뢰된 시각을 먼저 확보해야 한다.

### 「인증서를 바꿨는데 브라우저가 여전히 경고한다」

자체 서명 인증서를 쓸 때, 브라우저의 예외는 **그 인증서 하나에 묶인다.**
인증서를 재발급하면 예외가 무효가 되어 경고가 다시 뜬다. 정상 동작이다.

### 「무결성 검증 대상에 인증서를 넣으면 안전하다」

인증서 파일을 무결성 매니페스트에 넣었다면, **재발급할 때마다 기준값을 갱신**해야 한다.
안 하면 다음 자체시험이 변조로 판정한다. 교체 절차에 갱신 단계를 포함시켜야 한다.
