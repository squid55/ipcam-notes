# 무결성 검증 · 서명 업데이트

> 무결성 검증은 「지금 이 파일이 원래 그것인가」를 확인하는 일이고,
> 서명 업데이트는 「이 펌웨어가 우리가 만든 것인가」를 확인하고 설치하는 일이다.

## 왜 필요한가

펌웨어가 바뀌었는데 아무도 모르는 상태가 가장 나쁘다. 기기는 정상처럼 동작하면서
공격자의 코드를 실행한다.

그리고 업데이트 경로는 **공격자가 가장 쓰고 싶어 하는 통로**다. 한 번 뚫으면
정당한 방법으로 원하는 코드를 심을 수 있다. 그래서 업데이트는 편의 기능이 아니라
보안 기능으로 설계해야 한다.

## 최소 이해 수준

- **무결성 검증의 기본형.** 기준값 목록(매니페스트)을 만들어 두고 현재 값과 대조한다.
  기준값은 파일 해시다.
- **기준값을 보호해야 한다.** 매니페스트를 고칠 수 있으면 검증이 무의미하다.
  HMAC 으로 묶거나 읽기 전용 영역에 두거나 서명한다.
- **언제 검사하는가.** 기동 시 한 번 + 주기적으로. 기동 시만 하면 실행 중 변조를 놓친다.
- **실패했을 때 무엇을 하는가.** 기록 · 통보 · 서비스 차단.
  **차단하지 않으면 검증의 의미가 절반으로 줄어든다.**
- **서명 검증은 쓰기보다 먼저.** 검증에 실패하면 플래시에 손도 대지 않아
  기존 버전이 그대로 남는다. 순서만 지켜도 「업데이트 중 벽돌」의 상당 부분이 막힌다.
- **서명은 인증서 체인으로.** 단순히 「이 공개키로 검증된다」가 아니라
  「신뢰하는 CA 까지 이어지는가 + 유효기간 안인가」를 확인한다.
- **신뢰 앵커는 이미지 안에.** CA 인증서를 초기화되는 영역에 두면
  공장 초기화로 신뢰 기반이 사라진다.

## 직접 해보기

### 1. 매니페스트를 만들고 대조하기

```bash
# 기준값 만들기
find /경로 -type f | sort | while read -r f; do
  printf '%s|%s\n' "$f" "$(sha256sum "$f" | cut -d' ' -f1)"
done > manifest.txt

# 나중에 대조
while IFS='|' read -r f h; do
  now=$(sha256sum "$f" 2>/dev/null | cut -d' ' -f1)
  [ "$now" = "$h" ] || echo "불일치: $f"
done < manifest.txt
```

### 2. 파일 하나를 고쳐 탐지되는지

```bash
echo " " >> /경로/아무파일
# 위 대조 스크립트를 다시 돌린다 → 그 파일이 나와야 한다
```

빠진 파일도 잡히는지 확인한다. `sha256sum` 이 실패하면 값이 비어 불일치가 되므로
삭제도 탐지된다.

### 3. 서명을 만들고 검증하기

```bash
# 서명용 키와 자체 서명 인증서
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -sha256 \
  -days 365 -nodes -keyout sign.key -out sign.crt -subj "/CN=fw-signer"

# 서명
openssl dgst -sha256 -sign sign.key -out fw.sig fw.bin

# 검증
openssl dgst -sha256 -verify <(openssl x509 -pubkey -noout -in sign.crt) \
  -signature fw.sig fw.bin
```

`Verified OK` 가 나와야 한다.

### 4. 변조가 걸리는지

```bash
printf '\x00' >> fw.bin
openssl dgst -sha256 -verify <(openssl x509 -pubkey -noout -in sign.crt) \
  -signature fw.sig fw.bin
```

`Verification failure` 가 나와야 한다. 한 바이트만 바뀌어도 걸린다.

### 5. 순서가 중요한 이유를 재보기

업데이트 스크립트를 읽고 **검증이 쓰기보다 앞에 있는지** 확인한다.
없으면 검증 실패 시점에 이미 플래시가 절반 쓰인 상태가 된다.

```
좋음:  서명 검증 → (성공) → 플래시 쓰기
나쁨:  플래시 쓰기 → 검증 → (실패) → 되돌리기 시도
```

## 더 들어가면

- **dm-verity** — 블록 단위 해시 트리로 읽기 전용 루트를 검증한다.
  파일 단위 대조보다 촘촘하지만 읽기 전용 파일시스템이 전제다.
- **검증 부팅(Verified Boot)** — 각 단계가 다음 단계를 확인하는 사슬.
  최상단 키를 칩 내부 OTP 에 넣는데 그 기록은 되돌릴 수 없다.
  → [U-Boot](../BSP/U-Boot.md)
- **A/B 이중화** — 두 벌을 두고 실패 시 되돌린다. 플래시 용량이 두 배 필요하다.
  용량이 부족하면 「설치 중 전원 차단」을 구조적으로 막을 수 없다.
- **롤백 방지** — 옛 버전으로 되돌리는 공격을 막으려면 버전 카운터가 필요하다.
  되돌릴 수 없는 저장소에 둬야 의미가 있다.
- **SBOM** — 이미지에 무엇이 들어 있는지의 목록. 취약점 대응의 출발점이다.

## 흔한 오해

### 「해시 목록만 있으면 무결성 검증이다」

목록 자체가 보호되지 않으면 공격자가 파일을 고친 뒤 목록도 고친다.
**기준값의 무결성**이 먼저다.

### 「기동 시 한 번 검사하면 된다」

실행 중에 파일이 바뀌면 다음 부팅까지 모른다. 주기 검사를 함께 둔다.
다만 주기 검사 결과를 매번 기록하면 로그가 범람하므로,
**실패할 때만 기록**하고 복구도 한 번 기록하는 편이 실용적이다.

⚠ 실패만 기록하면 「미해결 실패가 영구히 남아 있는 것처럼」 보인다.
복구 기록이 없으면 「이 실패는 언제 해소됐나」에 답할 수 없다.

### 「검증에 실패하면 서비스를 멈춘다고 적어두면 된다」

문서와 구현이 갈리기 쉬운 지점이다. 실측: 검증 실패 시 「서비스 차단」이라고 기록에
남기고 있었지만, 실제로는 플래그 파일만 만들고 **다음 부팅 때 init 이 그것을 보고**
차단하는 구조였다. 실행 중에는 아무것도 멈추지 않았다.

기록 문구가 하지 않은 일을 했다고 말하면, 그것을 믿고 「이미 차단됐다」고 판단해
대응이 늦어진다.

### 「인증서 파일을 매니페스트에 넣으면 더 안전하다」

넣어도 되지만, **재발급할 때마다 기준값을 갱신**해야 한다.
안 하면 다음 검사가 정당한 교체를 변조로 판정한다.
교체 절차에 갱신 단계를 포함시켜야 한다.

### 「서명만 검증하면 충분하다」

서명이 유효한지와 **누가 서명했는지**는 다른 문제다.
공격자가 자기 키로 서명하고 자기 인증서를 함께 보내면 서명 자체는 유효하다.
신뢰하는 앵커까지 체인이 이어지는지 확인해야 한다.
